# 长期工程记忆：开发迭代与实测结果

日期：2026-11-15。基线为 `baa8c23ef1290198e4f390500da65758db131bff`（v0.3.4）；本分支为未发布的工程记忆改进。

**本轮完成了三个可复现改动，并在已公开的合成开发任务上验证。没有调用编码 LLM，没有测真实用户数周的工程生产率，也没有完成全面竞品胜出验证。**

完整协议见 [engineering-memory-evaluation.md](engineering-memory-evaluation.md)。全部逐例结果、原生响应、失败中间候选和源码快照在 [证据目录](../benchmarks/results/engineering-memory-20261115/)。[机器汇总](../benchmarks/results/engineering-memory-20261115/summary.json) 可以用保存的数据重算。

## 1. 改动及实际适用范围

1. **同会话原文的顺序。** 明确询问 current/latest/当前时，在相同任务和相同命中词集合内，使用原始 source_ref 的 turn_index 优先同会话中的后续匹配原文，不判定该原文是否正式取代旧决策。不同会话的 turn 编号不相互比较，同一 turn 的续页保持相关性次序。
2. **同页中的完整后续修正。** 字符预算会截断一个包含多个 turn 的页面时，若最新匹配 turn 完整放得下，先在同一读取快照中核对原始 turn 文本与坐标，再返回该连续原文。已经选定该 span 时，精确 token 打包也只从这一 turn 选完整单位。
3. **避免相同原文占满结果。** 仅 current、limit>1 且非已识别事件统计查询，在原有有界候选池中按项目、任务和完整原始正文精确分组，先选不同正文，重复来源必要时回填。原记录、page ID、source_refs 和候选计数保留；代码标点不同的正文不合并。

缓存版本从 10 升为 13；schema 保持 3，默认路径仍无需模型或新增依赖。历史和普通查询不启用这些 current 偏好。事件计数/频率/顺序 guard 只关闭第 3 项，并非承诺这类问题一定具有完整证据。

## 2. 实验身份与统计边界

工程数据为 8 个项目、4 个算法类别、6 个时间检查点、80 个问题；72 个问题有标注证据，48 个进入固定消费者策略检查。类别涵盖负边最短路、Top-k 同分规则、数据切分、全遮罩 softmax。只摄取任务之前的历史前缀，包含同 source ID 的原子替换。

固定消费者已知算法 family、配置格式和允许的策略集；从实际返回原文提取配置后运行手写小算法变体。因此其通过率是显式工程策略恢复及应用的代理指标，不是生成代码准确率。80 个问题来自少数相似模板，不能当作 80 个独立真实工程项目。

最终顺序为基线／候选／候选／基线，每块分别运行定向回放、工程回放和真实外部搜索组件。总计 2,880 次定向调用、7,680 次内部策略调用、1,920 次外部组件矩阵搜索。重复调用只用于计时；质量案例不重复计数。

- 基线 runtime SHA-256：`4f84e9f8e7fa0ee7c9abe1910f2df5622d0414fb5f3b6e218544161f8a25dd81`。
- 候选 runtime SHA-256：`107d5d7654a201d074decaa1c0b0e2b80c8f4cd409cdb37f4fb7d490a34da8ef`。
- 工程数据 SHA-256：`87e8ccad3510fb7e8a4c68c9fa3f284473abf8381ef6444ad179e3d4196b3ac3`。
- 所有工程、组件与定向记录均通过来源、字符预算和重复输出检查；16 个普通/历史控制案例的完整输出在全部重复中一致（仅剔除 latency_ms）。
- 结果缓存关闭，未清空 SQLite/操作系统缓存；计时是本机 Python 调用/上下文组装或各组件明确界定的搜索边界。开发数据已用于发现问题和设计改动，不属于独立 holdout。

## 3. 定向的长期会话修正

8 个中英配置案例使用相同会话中的旧值与后续修正，另有 16 个历史/普通控制案例。500 字符、limit=1。原版完整修正可见数为 **0/8**；第 1 候选 **4/8**；第 2 和最终第 3 候选 **8/8**。未修改 fixture 来消除失败。

| 指标 | 原版 | 最终候选 | 变化 |
|---|---:|---:|---:|
| 当前查询 p50 | 1.513 ms | 0.796 ms | -47.40% |
| 当前查询 p95 | 2.208 ms | 1.175 ms | -46.79% |
| 完整后续修正 | 0/8 | 8/8 | 8 个已知开发案例修复 |

每个版本的 current 计时合并 480 次调用；p95 使用 nearest-rank。这里的新证据更短，减少了对旧重复文本的截取工作。这只支持该工作负载下的本地检索改善，不能换算为大模型回复速度或整个产品加速。

## 4. 按时间推进的工程回放

使用各自原生预算内摘要。Book/flat 共用 scope、limit=5、索引和原文；recent_history 使用更短引用头、内存中原文且无 top-5 限制，作为实用策略对照单列。

| 字符预算 | Book 完整证据：原版 → 候选 | 固定消费者检查：原版 → 候选 | 获得/失去完整证据 |
|---:|---:|---:|---:|
| 1200 | 58.33% → 88.89% | 41.67% → 91.67% | 22 / 0 |
| 2400 | 61.11% → 94.44% | 41.67% → 91.67% | 24 / 0 |

2,400 字符下，完整证据由 44/72 提高到 **68/72**，固定消费者由 20/48 提高到 **44/48**。1,200 字符下为 42/72 → 64/72。flat 的完整率仍为 63.89%/69.44%，recent_history 为 44.44%/77.78%；无记忆消费者在这套必须恢复项目约定的规则测试中没有可提取配置，不能外推为真实 LLM 的零成功率。

**增加的延迟也保留：**

| 字符预算 | p50 原版 → 候选 | p95 原版 → 候选 | p95 变化 |
|---:|---:|---:|---:|
| 1200 | 1.842 → 1.825 ms | 3.563 → 3.793 ms | +6.46% |
| 2400 | 1.027 → 1.117 ms | 1.986 → 2.056 ms | +3.54% |

这里每版本每预算合并 480 次调用，p95 按评测器的线性插值计算。2,400 字符下候选平均上下文 1,812.0 字符，原版为 1,954.6375，减少约 7.30%。更好的证据质量伴随部分额外读取成本；没有宣称所有查询变快。8 个缺证据问题仍都返回相关非空上下文，不能把它视为答案，也不能据此计算幻觉率。

## 5. 实际开源组件对比

运行了原封不动的 `ranxianglei/billion-context@9674cfafbc78c50245ae0d887483d3d6ce880c15` 搜索内核，经现有锁文件校验，由 Node 24.22.1 执行。两边得到相同完整页面、项目范围和 top-5 限制，再使用同一完整块打包规则；不使用 Book 更灵活的原生摘要来代替这项公平对照。

| 字符预算 | 组件 | 证据召回率 | 完整证据率 | 固定消费者检查 |
|---:|---|---:|---:|---:|
| 1,200 | Book 原版/候选（本投影相同） | 65.00% | 61.11% | 41.67% |
| 1,200 | billion-context 固定内核 | 90.00% | **88.89%** | **83.33%** |
| 2,400 | Book 原版 | 65.00% | 61.11% | 41.67% |
| 2,400 | Book 最终候选 | **95.00%** | **94.44%** | **91.67%** |
| 2,400 | billion-context 固定内核 | 90.00% | 88.89% | 83.33% |

2,400 字符下，Book 相比该固定内核的完整率高 5.56 个百分点：逐题得到 6 个、失去 2 个完整证据案例。1,200 字符完整块预算下仍明显落后：得到 6 个、失去 26 个案例。原因之一是前排长维护块占用预算，后续有用整块被丢弃；这是下一轮应解决的真实成本，而不是删除该预算。

该对照仍有边界：Book 保留原生层级/FTS 元数据，Billion 使用统一消息字段；Book 测量进程内 recall 和原生上下文组装，Billion 分列搜索内核和持久进程 JSON 往返，公共 pack 另计。不能据此声称完整产品加速，也不能把它推广到最新版本或 Mem0、Graphiti、Letta、claude-mem。它们本轮只核查官方设计，没有重跑。Billion 的原始许可及额外产品表面归属要求沿用[适配器说明](../benchmarks/competitors/README.md#pins-and-attribution)。

## 6. 验证、保留记录和剩余限制

针对性回归 156 项通过，包含新增 18 项 current 检索测试、真实双 tokenizer 和 MCP 测试。最终本地完整套件运行 **991 项测试：976 项通过、15 项因缺少可选依赖跳过，零失败、零错误**，耗时 81.734 秒。跳过项为 PyArrow 相关 12 项、NumPy 相关 3 项；这不等于所有可选环境或 GitHub CI 已通过。完整命令、环境、源码身份和日志在 [validation.json](../benchmarks/results/engineering-memory-20261115/validation.json) 中独立记录。

- 三个候选的源码与测试快照、改动前失败日志均保留。最初组件作者尝试在准备依赖时中断，查询和评分均为零；其 interruption.json 同样保留。
- 初次全套检查因 sparse checkout 缺少历史报告 fixture 报错；已恢复所需原始文件，初次日志保留。运行时源码与 HEAD 不一致引发的历史 pin 校验也未算作有效生产回归。新增独立评测模块还暴露旧 round2 单元测试对当前目录的耦合：测试现使用原注册文件集合，并保留真实文件 hash 核验及新增/缺失/篡改拒绝断言；实际恢复校验和旧冻结证据未修改。
- 另一协作 Agent 对 3,840 个保存上下文重评分、从原生 hits 重建 1,280 个组件 pack，并复核全部定向记录，重算与汇总一致。该复核复用已有评分/打包函数，并非独立标签真值审核或人工审计；详情见 [independent-recomputation.json](../benchmarks/results/engineering-memory-20261115/independent-recomputation.json)。
- 每条 FTS 路由最多 96 项，重排池最多 limit×4 项，仍有容量边界；池外修正无法由本补丁恢复。只提配置名不提供值的不同正文，也可能挤占证据。
- **纯 token 截断仍有缺口。** 当字符预算足够容纳整页、只由 token 上限迫使截断时，本次同页修正偏好不触发。独立复核的 4,000 字符/90 token 例子仍返回旧 turn，原版相同。不得表述为“任意 token 预算都保证最新事实”。
- 事件查询 guard 为启发式，只控制重复正文压后；计数或时间线完整性仍需更完整的事件实验。
- `HTTPParser` 与 `http_parser` 等 acronym 命名变体的词法差异仍存在，处理它需要明确索引迁移和兼容验证。
- 本轮没有验证真实仓库隐藏测试成功率、第一次正确补丁时间、长期模型调用成本或真实跨项目经验迁移。

## 7. 复现

基础环境 Python 3.12.14、SQLite 3.53.1（精确值以每份 report.json 为准），原始报告保留完整环境信息。安装仓库开发依赖后运行：

```bash
PYTHONPATH=src python -m benchmarks.current_turn_replay \
  --output .artifacts/current-turn.json --repeats 30
PYTHONPATH=src python -m benchmarks.engineering_workflow \
  --output .artifacts/engineering-workflow --repeats 3 --budget-chars 1200 2400
PYTHONPATH=src python -m benchmarks.engineering_components \
  --output .artifacts/engineering-components --repeats 3 --budget-chars 1200 2400
python scripts/summarize_engineering_memory.py \
  --input benchmarks/results/engineering-memory-20261115/final \
  --output .artifacts/engineering-summary.json
```

组件首次运行下载锁定源文件；已有校验缓存后可加 `--offline`。原版可从基线 commit 独立 checkout 并通过 PYTHONPATH 导入，同一评测器保持不变。完整执行参数见 [execution.json](../benchmarks/results/engineering-memory-20261115/final/execution.json)。
