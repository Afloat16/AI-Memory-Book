# v0.14 long-history experiment protocol

This is a new experiment. It does not alter the v0.13 frozen protocol, its
failed attempts, or its measured limitations. The new evaluator retains the
old source-generating rules and 72 questions, changes the nuisance seed, adds
16 explicit missing/partial questions, and expands the main scale to 200,000
real ingested pages. It is authored synthetic development data. The separately
frozen real-project holdout must be reported separately.

## Registered matrix

| Stage | Pages | Controlled difference |
|---|---:|---|
| age-reference-1024 | 1,024 | Reference |
| age-shift-3650-1024 | 1,024 | Uniform 10-year source-timestamp shift |
| age-shift-7300-1024 | 1,024 | Uniform 20-year source-timestamp shift |
| foreign-10016 | 10,016 | Foreign similar-project growth only |
| foreign-50016 | 50,016 | Foreign similar-project growth only |
| foreign-100000 | 100,000 | Foreign similar-project growth only |
| own-200000 | 200,000 | Six target histories grow; foreign sources fixed |
| interleaved-200000 | 200,000 | Same logical sources and page IDs, interleaved insertion |
| replacement-200000 | 200,000 | Six existing configuration sources are replaced |

Two archived targets retain 16 pages throughout. Larger active targets must be
reported separately: a bounded small-project optimization does not establish
bounded access to long histories within a growing target. The optional
`expanded` profile adds 350,016 and 500,000 pages. Unexecuted stages are not
evidence. `development` is a 192-page plumbing diagnostic with an explicit
manifest label; it cannot satisfy formal scale or holdout requirements.

The generator uses real `MemoryBook.ingest` with turn segmentation. It does
not populate tables directly. Content, identities, turn boundaries and gold
are deterministic. The age controls must preserve all non-date source bytes
and physical order; layout controls must preserve logical-source and page-ID
hashes while changing physical insertion order.

## Distinguish evidence from answers

Each arm/stage executes all 88 quality questions: 56 fully answerable recall
requests, 16 missing recall requests, eight partially answerable recall
requests, and eight directory requests. Every returned quote is checked against
reconstructed project/session/turn coordinates, including Unicode positions.
The scorer rejects invented text, foreign project sources, invalid coordinates,
and replaced source payloads even if a result uses the expected source ID.

For a partial request, finding the known clause records
`available_evidence_complete`; it does not make the entire request answerable.
For absent identifiers, the scorer separately records an explicit
`evidence_coverage` signal with `scope=returned_excerpts` and the actual missing
identifier. Missing metadata is reported as unassessed. A nonempty context is
neither automatically a correct answer nor automatically an incorrect answer.
Literal identifier mention does not establish an approved value, authority,
truth, or exhaustive archive coverage. Current declaration assessment is
recorded independently. This experiment measures retrieval and API evidence
signals, not LLM answer accuracy or coding-task success.

## Migration, query isolation and timing

Every stage first builds and fingerprints a baseline source database. A
separate candidate worker then restores that database and initializes the
candidate runtime without performing any retrieval. It must preserve source
table, logical-source and page-ID hashes and leave an empty recall-result
cache. The resulting candidate database is snapshotted separately. Its one-time
initialization wall time, CPU, lifetime peak RSS and storage growth are retained.

Subsequent arm blocks always restore their own snapshot into a fresh worker.
Baseline blocks never open the candidate database. Candidate blocks start from
the verified candidate-indexed snapshot. Source bytes are identical; derived
indexes intentionally differ. This separates one-time migration cost from
steady queries rather than charging a full index rebuild to every repeat.

Four rounds use `AB, BA, BA, AB`. Each selected query has eight repetitions per
round, giving 32 cold-result-cache calls and 32 immediate warm calls per
arm/stage. Directory chains also have 32 samples. Nine queries cover fixed old
projects, current/history, growing projects, multi-source evidence, replacement
and a missing exact identifier. Report p50, empirical nearest-rank p95,
minimum/maximum and failures by query and mode. There is no p99 claim.

The first recall in each fresh connection precedes quality and all other
retrieval. Its four samples per arm/stage are descriptive; initialization and
possible schema work are timed separately. Clearing the result cache does not
flush SQLite, helper or operating-system caches. Snapshot restoration itself
warms the filesystem cache, so none of these measurements is physical cold
boot latency.

After uninstrumented samples, each selected query also runs once per arm block
with SQLite progress and trace callbacks. `callbacks * 100` is a coarse VM work
proxy. It is **not a count of scanned rows or complete VM instructions**; small
statements and SQLite internals can affect callback granularity. Trace callback
count is likewise labeled as observed callbacks. Probe wall time is kept in a
separate mode and never pooled into uninstrumented latency. Report the
runtime's returned candidate count separately where exposed.

The main matrix contains exactly **11,520 API observations**: 1,584 quality,
9,216 repeated performance, 72 first-connection, and 648 instrumented probes.
These repeated authored questions are not 11,520 independent user tasks.
Fingerprinting, restoration, scoring, JSON and gzip writes, and resource
inspection occur outside API timers. Baseline construction cost is retained;
candidate bulk-ingestion throughput is not measured by baseline-built inputs.

## Running and retaining evidence

Before formal queries, commit these files and bind that exact protocol commit:

- `benchmarks/v014_scale.py`
- `benchmarks/v014_workload.py`
- `benchmarks/experiments/v014-long-history-plan.json`
- `tests/test_v014_scale.py`
- The unchanged dependency `benchmarks/v013_workload.py`

```bash
python benchmarks/v014_scale.py describe
PYTHONPATH=src python -m unittest tests.test_v014_scale -v
python benchmarks/v014_scale.py run \
  --protocol-commit EXACT_PROTOCOL_COMMIT \
  --baseline-root /absolute/path/to/baseline \
  --candidate-root /absolute/path/to/candidate \
  --candidate-commit EXACT_CANDIDATE_COMMIT \
  --backend python --profile main \
  --output /absolute/path/to/new-attempt
```

The baseline is fixed at `861b7f35ac2557024d89bc51d5b3017ca35cb9d0`. Both runtime
commits, all tracked runtime file hashes, actual imported package, backend and
native binary hash are checked. `native` requires an actual native extension
from each selected source tree; fallback is rejected. Runtime and evaluator
identities are checked again after workers finish.

Use `--resume` with the same binding to continue an interrupted attempt.
Completed slots are reused only once; failed attempts retain their journals,
stdout, stderr and original responses. Every response is saved as a separate
recoverable gzip member, with raw offsets and hashes in the observation journal.
Do not edit gold or omit failures after observing results. A protocol correction
requires a new protocol version and retention of the original attempt.

`measurements_completed` means the registered calls were executed and recorded.
It does not mean quality passed or that latency is bounded. Read the per-case
source errors, missing/partial scores, complete sample counts and all incomplete
cells before drawing conclusions. Initial migration is allowed to grow with
archive size and must be shown alongside any query improvement. Production
concurrency, adaptive segmentation, embeddings and LLM task outcomes are outside
this matrix.
