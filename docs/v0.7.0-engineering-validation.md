## Goal and preregistration

The engineering goal is book-like navigation with exact project identity:
project book → directory question → chapter/section/page → complete original
turn. Similar projects can reuse names, sessions, tasks and parameter names
without making a client silently retrieve another project's memory.

The [fixed protocol](../benchmarks/project_navigation-plan.md) and
[same-topic workload](../benchmarks/project_navigation_data.py) were registered
before quality retrieval. The dataset SHA-256 is
`589be00eb493fd05fc12dd59050e113a074cd0c2833c059848de50d0ffdfd74b`.
The production source, evaluator, existing engineering dataset, same-topic
dataset, two budgets, eight backends and three repeats require a matching
`project-navigation-freeze.json` before the hosted quality stage may run.

The existing original evaluators, scorers, packers, old dependency lock and
historical report files remain immutable. The new driver is checked against
the original component driver using complete response equality on every shared
case and budget, not just equality of aggregate scores.

## Runtime changes

- Recall resolves an explicit project, an exact chapter or the sole available
  project before reading its cache. With multiple books, an otherwise ambiguous
  request is rejected. Deliberate all-project search must opt in explicitly.
- Directory search uses title/question/directory fields only. Matching pages
  are grouped into section entries before pagination; returned metadata gives
  the next navigation address and exact original-source identity.
- Chapter, section and page reads accept the selected project as a guard. A
  mismatched book cannot return that address's source content.
- Original-turn pagination reads bounded source chunks independently of page
  splitting. A source-session hash can bind consecutive chunks to one stored
  source version; a replacement causes a refusal and a restart instruction.
- Nested directory navigation uses a SQLite read snapshot, preserving existing
  caller-owned transactions. Schema 4, source addresses, current-query ranking,
  the default 2400-character budget and the five-result limit remain unchanged.

The [navigation guide](book-navigation.md) states the API migration and limits.
Scope guards are not authentication or authorization. Directory search is
lexical and does not prove all relevant questions have been found. A complete
source turn is the stored normalized conversation, not a guarantee that its
contents are correct or current.

The new cohort has eight exact project IDs with one display name, four source
checkpoints, reused session/task identities, conflicting algorithm policies and
parameter values, interleaved ingestion and in-place source replacement. All
methods receive the unchanged query and correct project ID. It measures behavior
with an explicitly supplied identity, not the ability of a language model to
infer the intended project from an ambiguous sentence.

Each backend receives the same current original pages, with its registered
index metadata and native scope before top-five retrieval. The common packer
includes source headings and separators in its budget and skips oversized whole
blocks. It does not substitute the native Book excerpt track. External indexes
are rebuilt from each visible checkpoint; this does not evaluate every product's
incremental update/delete lifecycle.

ReMe uses a separately locked environment and actual upstream
`DefaultFileChunker` / `LocalFileStore` BM25. Embeddings are disabled and no LLM
object is constructed. Source files use complete original page text, and native
chunks must match the registered source/line mapping exactly. The exact project
ID selects a native paths collection before top-five search. It does not use a
custom rewritten BM25, custom corpus-specific tokenizer or answer-aware query.

Mem0, Chroma and LangGraph share the same pinned MiniLM representation, so their
outcomes are correlated configurations. Basic Memory uses explicit FTS and Mem0
uses `infer=False`; neither measured component represents the full default
product. ReMe, Basic Memory, OpenViking and Hindsight already offer useful project
or file/directory mechanisms. The comparison does not claim those ideas are
unique to Book. See the [eighteen-family source review](open-source-memory-comparison.md).

## Separate native navigation contracts

Thirty-two registered directory requests exercise title, task/directory,
body-only negative and absent-metadata queries. The checker verifies the absence
of body fields and detects a whole answer body hidden under a metadata key; short
question summaries are also checked against their actual original questions.
Eight directory-to-original roundtrips reconstruct source evidence with bounded
reads, and twenty-four wrong-book chapter/section/page requests have valid
same-book controls. Empty, sole-book, ambiguous, session-only, exact-chapter,
explicit-global, invalid-blank and conflicting-scope recalls are recorded
separately. Source guards and full original-turn continuation also have direct
runtime regression tests, including replacement between source chunks.

Every contract stores actual API calls, returned responses, failures, character
and UTF-8 traffic sizes and timings. An independent retained-output audit checks
source coordinates, reconstructed text, exact request parameters and metric
denominators. These tests are not a latency comparison against competitors and
do not certify multi-user isolation.

## Frozen production identity

The independent runtime review confirmed scope resolution before cache/FTS,
unchanged project/chapter/session intersections, source snapshot consistency
under a concurrent writer, bounded original-turn reads and rejection of a stale
source hash. The remaining documented limits are optional guard/hash arguments,
separate snapshots across directory pagination calls, exact-ID false negatives
for surrounding whitespace in the existing recall path, and optional model/
tokenizer initialization before the ambiguity error. None silently widens the
requested project scope.
