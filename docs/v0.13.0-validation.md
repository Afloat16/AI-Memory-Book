# v0.13 longitudinal memory development and validation

**Status: source accepted for measured evidence-completeness and directory
improvements; exact release delivery gates remain separate.** The second
100,000-page experiment recovers all required multi-source evidence under the
unchanged protocol. Its independent audit passes. Cold-recall regressions and
archive-size-dependent costs remain explicitly accepted limits. The
[source decision](../benchmarks/experiments/v013-source-acceptance.json)
does not declare every original objective achieved. The published installation
at this preparation checkpoint remains v0.12.0; v0.13 publication needs its own
final-source CI, native builds, public installation and delivery audit.

## What this work is testing

The engineering goal is to find the right original evidence in a named project
after years of revisions, even when many other projects use similar algorithms,
field names and maintenance language. The measured outcomes are evidence
coverage, source order, exact project/source integrity, navigation correctness
and API latency. They are not LLM answer accuracy or production task success.

There are separate controls for the age of timestamps, growth of other similar
projects, growth of a target's own history, interleaved insertion order and
replacement of an existing source. A project being old and a database being
large are different conditions. A fast query with incomplete evidence is still
incomplete and remains in both the quality record and the timing record.

## Scale matrix that actually ran

The main matrix uses real `MemoryBook.ingest`, explicit turn segmentation and
four algorithm families. Eight target projects initially have 16 pages each;
two archived projects retain that size while six active/new projects acquire
long histories. At 100,000 pages there are 788 projects, including 780 similar
foreign projects. This is an authored development fixture, with repeated
maintenance text, rather than an unseen archive or independent holdout.

| Checkpoint | Pages | Projects | Controlled change |
|---|---:|---:|---|
| `age-reference-1024` | 1,024 | 22 | Small reference archive |
| `age-shift-1024` | 1,024 | 22 | Same content/order; all timestamps 3,650 days earlier |
| `foreign-10016` | 10,016 | 163 | Only similar foreign-project growth |
| `foreign-50016` | 50,016 | 788 | Further foreign-project growth |
| `own-100000` | 100,000 | 788 | Six targets acquire their own long histories |
| `interleaved-100000` | 100,000 | 788 | Same logical sources/page IDs, different insertion order |
| `replacement-100000` | 100,000 | 788 | Six existing configuration sources revised |

Each version/checkpoint executes 64 recall quality queries and eight directory
quality queries. Of the 64 recall queries, 56 have required evidence, comprising
64 spans; eight ask for absent evidence. These same questions repeat across
checkpoints and are not independent samples.

Performance uses seven recall queries and two complete directory chains, six
balanced rounds in order `AB, BA, BA, AB, AB, BA`, and separately restored
baseline-built snapshots for each arm. Each recall query/version/checkpoint has
30 cold-cache calls and 90 immediate warm-cache calls. Each directory query has
30 calls. The full run contains **84 execution blocks, 1,008 quality calls and
12,600 performance calls: 13,608 total**. All main cells completed in each run. The
optional 200,000-page extension was not selected or executed.

Here "cold" means the recall-result cache is cleared before timing, not that
the operating-system or SQLite page cache has been evicted. Directory timing
includes discovery, section access and original-page reading. Snapshot restore,
database opening, scoring and result journaling are outside the query timer.
The report separately records initialization, database size, CPU time and
process-lifetime peak RSS. Peak RSS is not per-query allocation.

## Run 1: retained failures and measured benefits

Both versions had exactly the same quality scores and evidence projections at
all 504 quality configurations per arm. The candidate added assessment metadata
and warnings; those JSON changes did not improve evidence coverage.

| Outcome, per version across seven stages | Baseline | Run-1 candidate |
|---|---:|---:|
| Complete answerable recall configurations | 336/392 | 336/392 |
| Required recall spans | 392/448 | 392/448 |
| Current source ranked first, where applicable | 80/168 | 80/168 |
| Complete directory evidence | 56/56 | 56/56 |
| Missing-evidence queries returning context | 56/56 | 56/56 |
| Saved-source errors / cross-project output | 0 | 0 |

At every stage, recall completeness was **48/56**, with **56/64** required
spans. All eight multi-source questions retrieved the boundary constraint but
omitted the current policy. Their final result lists contained the boundary
page and four maintenance pages. The current policy was present in the candidate
pool, so this was a final-selection/ordering problem, not missing ingestion.
The corresponding performance query was also incomplete in 840 calls per arm.
All these outputs and timings remain in the original artifact.

English current-state queries initially ranked old policy above current policy.
After own-history growth, both versions changed rank together, including the
two unchanged archived projects. That corpus-dependent change is not a
candidate improvement. The timestamp-shift and interleaving quality controls
preserved evidence projections within each arm. These observations do not
establish calibrated abstention or general factual authority.

| Run-1 performance outcome | Observed result |
|---|---|
| Cold recall p50 | Candidate slower in 41/49 query-stage groups, slightly faster in eight |
| Warm result-cache p50 | Candidate slower in all 49 groups |
| Complete directory-chain p50 | Candidate faster in all 14 groups |
| Archived project, 100k grouped layout, directory p50 | 99.038 ms baseline → 6.380 ms candidate; 15.52× |

The archived directory p50 still grew from about 0.55 to 1.06 to 3.25 ms as only
foreign history grew. The large grouped-layout speedup must therefore be shown
alongside the interleaved result and the remaining growth cost. Run 1 does not
support constant-time old-project access or an end-to-end recall speedup.

The measured host used Ubuntu 24.04, Python 3.12.16, SQLite 3.45.1, GCC 13.3 and
an Intel Xeon 6975P-C with four logical CPUs. The largest retained snapshot size
was 384,495,616 bytes. The independent ZIP audit checked **166,409 integrity
conditions, 13,608 original responses and 66,136 source references**, including
every score, source coordinate, raw gzip member and timing statistic. It did
not execute new retrieval calls or restore the excluded CI SQLite databases.
See the [complete review](../benchmarks/reports/v0.13-development/scale-run1-review/scale-run1-summary.md)
for every latency group, p95, source identity and limitation.

## Smaller diagnostics do not override a scale failure

The earlier corrected development source `9715042` completed the unchanged
62-question diagnostic on both Python and native backends: 496 responses per
backend across budgets, limits and temporal modes. In each auto-mode cell,
all 38 answerable current first-source cases passed. The previous 38-question
diagnostic's 32 answerable first-source cases also passed, with 304 responses
per backend. The original results retain their actual source labels; a
[38-file equivalence receipt](../benchmarks/reports/v0.13-development/final-version-equivalence/equivalence.json)
shows that run-1 source `9ea37a7` changed only the two package-version literals
relative to that runtime.

Those are bounded current-source diagnostics. Across all case kinds in the
62-question fixture, a one-result limit contains 48/66 required spans; a
five-result limit contains 66/66. Equal-time conflicting sources cannot both
fit in a one-result response. Four of six missing-evidence cases still return
context. The metadata reports bounded candidate-pool uncertainty and conflict
pointers; it does not decide which conflicting fact is true or make a
whole-archive completeness guarantee.

Run-1 source separately passed the unchanged legacy engineering replay:
800 responses per runtime, zero score changes or regressions; Book retains
72/72 complete cases, 80/80 spans and 48/48 policy checks at both budgets and
packing tracks. Each backend's short-page controls preserved all 434 prior
positive cases among 482 configurations, retaining the 48 insufficient-budget
controls. Each backend passed 119 directory contracts with 597 recorded
operations and 161 original-page reads. These records are in the
[legacy gate summary](../benchmarks/reports/v0.13-development/legacy-gates/summary.json).
They do not turn run 1's 48/56 scale completeness into a pass.

Ordinary CI `44314079392/1` passed ten of eleven jobs. Its MCP job discovered

The [complete 112-group table](../benchmarks/reports/v0.13-development/scale-run2-review/scale-run2-summary.md)
retains all p50, p95, paired-round statistics and resources. For the archived
project at 100k interleaved pages, current cold recall falls from 166.898 to
102.478 ms, historical cold recall from 133.222 to 67.912 ms, and full directory
navigation/read from 159.154 to 26.707 ms. Grouped-layout archive directory
latency is 157.307 → 9.958 ms; it must not hide the interleaved case.

Costs remain substantial in some groups. At 1,024 pages archived-current
cold recall rises from 6.726 to 10.516 ms although both versions return complete
evidence. Multi-source cold recall rises from 7.235 to 11.316 ms, with incomplete
baseline and complete candidate evidence. All seven slower warm groups are
that multi-source query, increasing approximately 6.36–9.33%. At 100k interleaved
pages active-current cold recall rises from 332.062 to 338.309 ms. Small measured
differences are not statistical significance claims.

For an unchanged 16-page archived project, candidate directory p50 grows
0.7692 → 1.5787 → 4.9298 ms as total foreign-heavy history grows through
1,024 → 10,016 → 50,016 pages. The goal of archive-size-independent response
time remains unmet. Global FTS statistics/postings and physical layout still
contribute work; bounded returned rows are not bounded total database work.

The timestamp-shift and insertion-order controls preserve all 72 evidence
projections in each arm. They separate timestamp age from archive growth;
they do not guarantee constant future latency. Run 2 used an AMD EPYC 7763
host, Ubuntu 24.04, Python 3.12.16 and SQLite 3.45.1, with four logical CPUs.
Run 1 used a different hosted CPU, so its absolute times must not be treated
as paired before/after measurements of the corrections.

Initialization medians are approximately 0.80–0.85 ms in the retained stages.
At 100k grouped/interleaved pages, final databases occupy approximately
363.457/366.715 MiB in both arms. Process-lifetime high-water RSS is approximately
52.102/53.453 MiB in those layouts; this is not a per-call memory measure. The
small reference stage has baseline/candidate peaks of about 35.283/37.100 MiB,
so universal memory savings are not established. Worker CPU includes scoring,
fingerprinting and journaling outside API timers; round zero additionally
executes 72 quality calls. The full resource table retains those boundaries.

## Acceptance boundary

The [source decision](../benchmarks/experiments/v013-source-acceptance.json)
accepts runtime `a7492a74a94170b87a2fd54ada421866b9d737f46dce2ff3a3bc21d6debb9da1`
for the measured completeness and directory benefits while retaining the
cold-recall costs and unmet goals above. Accuracy has priority over labeling
incomplete fast responses as successful. This is a scoped release decision,
not a declaration that every original optimization target has passed.

Publication additionally requires exact release-source CI, all 30 native
build/install cells, the real public installer and the independent original-byte
delivery audit under the existing [release procedure](releasing.md). Their
results must be recorded separately after execution; no v0.12 delivery count
is reused as v0.13 evidence.

The historical external-component comparisons retain their own pinned runs.
Neither the scale experiment nor its internal baseline is a fresh benchmark
of every external open-source product. No result here establishes universal
superiority, unseen real-project correctness, LLM answer accuracy, calibrated
abstention or constant-time retrieval as the archive grows.
