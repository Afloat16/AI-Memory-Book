# v0.4.0 — Current engineering evidence with a 2,400-character default

Release scope: **the C3 current-evidence improvements and a 2,400-character,
five-result default**, using local lexical retrieval. This version is prepared
for the normal GitHub release channel (`prerelease=false`). Publication requires
the exact final source to pass the release gates below; this source document
does not by itself establish that the tag, public assets or public installation
checks have completed.

## Default behavior

| Setting | v0.4.0 default | Caller control |
|---|---|---|
| Assembled context | 2,400 characters, including citation headings | Explicit `budget_chars`, or CLI `--budget` |
| Returned pages | Up to five | Explicit `limit` |
| Retrieval | Local lexical `book` strategy | Semantic retrieval remains opt in |
| Coverage expansion | Disabled | Explicit `coverage=true` |
| Exact token cap | None | Explicit `budget_tokens` and supported tokenizer |
| MCP references | Compact references with source identity | `details=true` exposes exact source spans |

The previous omitted character allowance was 4,000. An explicit 4,000-character
request is still supported. Python, CLI and HTTP responses retain their detailed
source fields. The context cap does not limit all protocol metadata and is not a
model-token count. No model, embedding download or new core dependency is
introduced by these defaults.

The selected 2,400-character setting is the stronger of the two engineering
budgets measured in this development study, 1,200 and 2,400 characters. It is not
claimed to be optimal for every project or better than every untested budget.

## What changes in current-evidence recall

- **Order comparable corrections inside one session.** Explicit current/latest/
  当前 queries can prefer a later matching original turn in the same task and
  session. Turn numbers are not compared across sessions, and continuations of
  one turn keep their relevance order. This is evidence ordering, not a claim
  that a later statement authoritatively replaces every earlier decision.
- **Preserve a complete later turn when a page is shortened.** If a character
  allowance truncates a page containing several turns and a complete later
  matching turn fits, verify its text and coordinates against the original turn
  within the same read snapshot. When this preferred span is selected, exact
  token packing uses complete units within that span.
- **Give distinct original pages space in the bounded candidate pool.** For
  applicable current queries, compare full raw page bodies within the same
  project/task and defer duplicate bodies behind distinct evidence. The newest
  duplicate keeps the group's relevance position. Original records, page IDs,
  citations and candidate counts are retained, and duplicates can backfill
  remaining result slots. Code punctuation differences remain significant.

Historical and ordinary queries do not activate these current preferences.
Recognized event-count, frequency and timeline queries bypass duplicate-body
deferral; that guard does not guarantee complete event-history retrieval.
Schema remains **3**. Recall-cache version **13** isolates new results from
cached responses produced by the earlier ranking behavior.

## Evidence used to select this release

The [engineering protocol](../engineering-memory-evaluation.md),
[full results and retained failures](../engineering-memory-results.md), and
[raw evidence directory](../../benchmarks/results/engineering-memory-20261115/)
identify the baseline, three candidates, evaluator source and every measurement.
These are synthetic development fixtures, already used during implementation;
they are not independent holdout tasks or real-user longitudinal measurements.

The numbers below were measured on the frozen **C3 development runtime with
explicit 2,400-character / five-result arguments**, before the v0.4.0 version
and default-setting changes. They support the selection of the release behavior.
Final release-source tests, packaging checks and public-install verification are
separate evidence; the historical timing samples are not relabeled as a fresh
benchmark run of the v0.4.0 package.

### Chronological engineering replay

The workload contains eight similar projects, four algorithm families, six
chronological checkpoints and eighty questions. Only the visible history prefix
is ingested. Seventy-two questions have required source evidence; forty-eight
also run a fixed configuration consumer.

| Measure at 2,400 characters | v0.3.4 baseline | Selected C3 runtime |
|---|---:|---:|
| Complete original evidence | 44/72 (61.11%) | 68/72 (94.44%) |
| Fixed-consumer strategy checks passing | 20/48 (41.67%) | 44/48 (91.67%) |
| Local retrieval p50 | 1.027 ms | 1.117 ms |
| Local retrieval p95 | 1.986 ms | 2.056 ms |
| Mean assembled context | 1,954.6 characters | 1,812.0 characters |

The quality gain includes 24 questions gaining complete evidence and none losing
it in this development cohort. The local p95 increases **3.54%** and remains part
of the release tradeoff. Average context length falls about **7.30%**. These are
local retrieval/context measurements, not time to a correct generated patch or
language-model response speed.

The fixed consumer knows the algorithm family, configuration syntax and allowed
policy set; it extracts an explicit setting from the returned context and runs
handwritten small algorithm variants. Its pass rate measures recovery and use
of that setting, not code generation or general algorithm implementation skill.
The eighty questions are correlated templates and checkpoints, not eighty
independent real projects.

### Scoped external-component comparison

The actual pinned `billion-context@9674cfafbc78c50245ae0d887483d3d6ce880c15`
search kernel was run on the same pages, project scopes and top-five boundary,
followed by a shared whole-block packer. At 2,400 characters, C3 has **94.44%**
complete evidence versus **88.89%** for that fixed kernel; the paired results
include six gains and two losses. Fixed-consumer strategy checks are **91.67%**
and **83.33%**, respectively.

The adverse 1,200-character shared-block result remains: Book has **61.11%**
complete evidence versus **88.89%** for that kernel, with six gains and twenty-six
losses. Interface/storage work differs, so no whole-product speed ratio follows.
The result does not establish superiority over newer revisions, Mem0, Graphiti,
Letta, claude-mem, or all dimensions of any product. The complete component and
native-budget tables remain in the [result report](../engineering-memory-results.md).

### Targeted corrections and limits

The separate eight-case current-turn replay improves complete correction
visibility from **0/8 to 8/8** at 500 characters and one result. Its local p95
decreases **2.208 → 1.175 ms**. Sixteen ordinary/historical controls preserve
their complete non-timing outputs. This narrower workload and budget are not
interchangeable with the engineering table above.

Known limits remain part of the release:

- Each FTS route supplies at most 96 candidates; current reranking sees at most
  `limit × 4` candidates. A correction outside that pool cannot be recovered by
  these preferences.
- Different low-value bodies can still crowd out a decision. Exact duplicate
  handling does not identify every semantic paraphrase or decide which source
  is authoritative.
- **Pure-token truncation is not covered by the same-page correction rule.**
  When a full page fits the character allowance but exceeds a separate token
  cap, the new preferred span is not established. A documented
  4,000-character/90-token case still returns the older turn, as the baseline did.
- Eight missing-evidence queries still return related nonempty context. No
  generated answer was measured, so these results do not establish an answer
  hallucination or abstention rate.
- Repeated-event completeness, code-version validity, acronym/identifier
  variations, real repository hidden tests and end-to-end agent task costs need
  further evaluation. Earlier rejected candidates and unfavorable observations
  stay in the linked evidence rather than being replaced by release packaging.

## Install and upgrade

Once the verified release assets are available, use the pinned installer:

```bash
curl -fsSLo install-memory-book.sh https://raw.githubusercontent.com/Afloat16/AI-Memory-Book/v0.4.0/scripts/install.sh
bash install-memory-book.sh
memory-book --version
memory-book setup --client claude-code
memory-book doctor
```

On Windows:

```powershell
Invoke-WebRequest https://raw.githubusercontent.com/Afloat16/AI-Memory-Book/v0.4.0/scripts/install.py -OutFile install-memory-book.py
py -3 .\install-memory-book.py
```

Python 3.10+ and SQLite FTS5 remain required. The installer downloads the release
wheel and includes MCP/client extras by default. Existing environments and
memory databases are preserved. Existing schema-3 archives need no reimport or
schema migration. Re-run setup with the new launcher, keeping the same database
and client settings, and reinstall an existing capture service so its absolute
Python path points at the new environment. See the [upgrade guide](../deployment.md#upgrading).

## Release-source validation and publication gates

The [release-profile verification](../../benchmarks/reports/v040-release-preparation/default-profile/report.json)
replays all eighty original engineering cases with omitted product options.
Every complete non-timing response equals both explicit `2400/5` calls and the
frozen C3 response; all source and budget checks pass. It retains **68/72**
complete-evidence cases and **44/48** fixed-consumer passes. This checks default
wiring and compatibility, without creating a new timing or holdout claim.
The initial verifier's optional-field aggregation failure is retained alongside
the corrected verifier output. The [selection record](../../benchmarks/reports/v040-release-preparation/selection.json)
binds this scope and its retained costs to the approved release runtime.

The [local release preflight](../../benchmarks/reports/v040-release-preparation/local-validation.json)
completed **995 tests: 980 passed, 15 optional-dependency skips, zero failures
or errors**. The skips require PyArrow (12) or NumPy (3). The prepared wheel and
sdist each installed in a separate clean environment and passed version,
source/reader-byte, recall and default-profile checks. These preflight artifacts
identify their preparation commit; final public assets are rebuilt and checked
by the exact-commit publication workflow below.

The [release workflow](../../.github/workflows/release.yml) and
[publisher](../../scripts/release.py) require all of the following before normal
publication:

1. Register v0.4.0's exact final runtime hash and normal release channel. The
   version in the package, runtime and three installers must agree.
2. Complete all nine jobs of the existing Tests workflow on the exact release
   source commit: three core Python versions, MCP, browser, three platform
   installers and container. Development-candidate results do not replace this
   exact-commit release gate.
3. Point `main` and `release/v0.4.0` at that same commit. Build the sdist and the
   wheel from it using pinned build tools; verify the committed runtime/reader
   bytes and install each package in an independent clean environment.
4. Publish and verify exactly seven checksummed assets: wheel, sdist, three
   installers, `release-manifest.json`, and `SHA256SUMS`. Tags remain fixed and
   existing public releases are not overwritten.
5. Verify the normal release/Latest identity, then install through the real
   public installer URL and check the package version, release-wheel route and
   default MCP/client dependencies.

The release body and manifest record the actual source identity and linked CI;
the public-installer job records its own result. These gates report packaging
and installation correctness separately from the retained C3 development
measurements. This distribution uses GitHub release assets, not PyPI.
