# v0.7.0 — keep directory and source reads in the selected project

AI-Memory-Book organizes an engineering archive as project books, task chapters,
question sections and original-evidence pages. This release carries an exact
project choice through follow-up reads, so a client working on similar services
or algorithm implementations can keep the selected book throughout its lookup.
The caller still chooses the correct project; the product does not infer that
choice from a directory name or guarantee that a model will use memory correctly.

## Engineering behavior

- Python `chapter`, `section` and `read`, their CLI commands, and the corresponding
  MCP/HTTP tools accept an optional exact project assertion. A foreign or unknown
  project cannot retrieve another project's chapter, section or page through an
  asserted read. A failed lookup does not retry globally.
- `memory-book mcp --project PROJECT_ID` binds one stdio connection. Omitted tool
  scopes inherit the binding, including `browse_book`; explicit conflicts fail
  before opening the database. Project listing is limited to the bound project.
  Enabled `remember_session` writes still need the matching explicit
  `payload.project`; messages are never silently reassigned.
- `setup --mcp-project PROJECT_ID` installs that binding in the selected client
  configuration. Ordinary setup preserves an existing managed binding. Change
  the ID explicitly or remove it with `--clear-mcp-project`. Capture's
  `setup --project` remains separate and still requires `--capture`.
- The reader includes the selected project in chapter, section continuation and
  original-page requests. Switching books invalidates outstanding reader results
  and errors, so an old response cannot repaint the new project's reader.

A binding applies to one configured connection, not automatically to a terminal's
current working directory, a different server or direct SQLite access. It is an
application scope constraint, not user authentication or an ACL. Unbound calls
retain archive-wide behavior. An explicitly empty HTTP recall `project=` now
returns HTTP 400 instead of being treated as an omitted scope; this intentional
compatibility change is recorded in the validation report.

Schema 4, original text and source IDs, recall ranking, default budgets and the
recall cache version remain unchanged from v0.6.0. Existing schema-4 archives need
no new schema migration. See [bound connections](../agent-guide.md#bound-project-connections),
[client configuration](../integrations.md) and [installation](../deployment.md#install-v070).

## Broader open-source comparison without unmeasured scores

The [official-source comparison](../open-source-memory-comparison.md) now covers
**19 external project families**, including store/retrieval infrastructure.
OpenViking, Serena, EverOS, SimpleMem and Supermemory are new source/documentation
reviews; their commits and reviewed source blobs are pinned. LangMem is a
supplementary SDK reference and is not counted as a twentieth family.

**No new external runtime comparison was executed in this iteration.** The README
keeps the six measured external components explicitly labeled as the frozen
v0.6.0 comparison: billion-context, claude-mem FTS, Basic Memory FTS, Mem0 raw
memory, Chroma and indexed LangGraph Store. Their configured modes, common-page
packing, local model, adverse 1200-character cases and measurement limitations
remain unchanged. Source review does not grant any unmeasured project a score,
and project scopes or hierarchical directories are not claimed as unique to
AI-Memory-Book.

## Installation and publication integrity

The Python, Bash and PowerShell installers target the v0.7.0 release wheel and
retain prior release routes. The default isolated installation includes MCP and
client support. Comparison dependencies, models and research reports remain
outside the normal package.

The approved release Python-runtime SHA-256 is
`4c73660bebe1e884aac689bd07b71671868fb58336d31d25841623607451239a`.
The distinct benchmark file-map digest is
`0d1197a55249bef509151277f589c4c69357febd472b2adf1706adb32c43b4ac`.
The frozen runtime is published in commit
`cf51473e841a3a38df7c7c857cf51e0e14eb1861`; later documentation and test-expectation
commits preserve those runtime bytes. The release manifest identifies the exact
final source commit and all packaged files, including the reader HTML.

Publication requires the existing nine-job CI gate, clean wheel and source
installation, downloaded asset checksum verification and a separate public
installer smoke. These are packaging and distribution checks, not reruns of
the engineering benchmark. Source commits are created with Afloat16's verified
identity; the release workflow does not create a source commit.
