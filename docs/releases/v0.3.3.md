# v0.3.3 — Reduce recall work and MCP output scheduling

AI-Memory-Book keeps original conversation evidence in a shared local archive
for AI clients.

v0.3.3 reduces repeated retrieval work and certified MCP output dispatch
while preserving complete default output. Its fixed numerical performance gates
and final-source historical compatibility checks pass against published v0.3.2.
Three startup costs are accepted through the original plan's independent resource review.

## Changes in this version

- **Combine native MCP output operations once per message.** On the verified
  official SDK 1.30.0 standard-stream path, run the original UTF-8 text write and
  its immediate flush in one default worker dispatch. The paired SDK flush
  acknowledges only that successful operation; independent flushes and failures
  keep the original delegation. The SDK still serializes and frames every
  message, reads stdin, and owns initialization, context and lifespan. No
  response batching, deferred flush or cross-message text buffer is added.
  Unknown SDK versions, replaced/custom methods or unsupported native streams
  use the original FastMCP stdio path. Normal result-cache costs remain intact.
- **Read original source turns together within one snapshot.** For ordinary
  multi-session recalls, a parameterized relation fetches the exact requested
  `(session_pk, ordinal)` pairs through the existing unique index. The batch is
  bounded to 400 pairs / 800 parameters and checked against actual SQLite
  limits. Python 3.10, custom factories, restrictive limits and unsupported or
  malformed inputs retain the original per-session path. Original source-map
  and projected-unit integrity checks remain in the same read transaction.
- **Reuse a captured source-reference parse once.** Final reference projection
  can consume the already parsed map for one ordinary span when the current raw
  reference object and the preparation, JSON and projection methods still
  match. Each page capture is exposed at most once. Multiple spans, repeated
  pages and custom or changed inputs retain the original parsing path, keeping
  `message_indices` and other nested containers independent. No internal fields
  are added to rows or results, and no source map persists across recalls.
- **Read narrow metadata during retrieval.** A covering index on
  `(rid,id,project_id,chapter_id,session_pk)` avoids loading wide page records
  for candidate metadata. Original content and source references remain fetched
  for final results. Unbounded chapter/session routes retain planner choice;
  existing scope predicates, global BM25, ordering and limits stay intact.
- **Read each directory once within a recall.** Candidate pages share chapter
  and session metadata. The new path fetches light candidate addresses and
  then each distinct directory pair once inside the existing read snapshot.
  All referenced rows and field types are checked before pruning; malformed
  metadata and custom factories keep the original path and errors.
- **Skip provably irrelevant scoring.** The existing title multiplier lies
  between 1 and 1.15. A strict score upper bound retains every candidate that
  can enter the original ranking/novelty pool, including ties, while preserving
  the complete original candidate count. Semantic, coverage and custom-callable
  paths remain unpruned. Query-result cache behavior is unchanged; bounded derived count reuse is described below.
- **Avoid repeated Python work.** Identical ordered lexical routes reuse their
  candidate mapping without building unused fusion maps. Native SQLite rows
  feed metadata by position, with the existing custom-row fallback retained.
  Directory overlap is computed once per directory within each recall call.
- **Reuse certified token counts.** Accepted blocks reuse their exact count
  when only a certified ASCII suffix can change after appending a separator.
  The inspected tiktoken 0.12.0 `cl100k_base` and `o200k_base` patterns, encoder
  identity and strict boundary checks remain prerequisites. Unknown patterns,
  custom counters and unsupported text retain full-count fallback behavior.
- **Remember exact counts of repeated evidence blocks.** A lazy memo owned by
  each connection holds at most 2,048 entries and 2 MiB of retained text objects,
  shared by both supported tokenizers. Keys retain the complete original text
  and certified encoder object identity. Unknown/custom implementations use the
  original exact path, and closing the connection releases retained text. The
  text cap excludes container/key/value/encoder overhead; actual RSS is measured
  separately. This is derived counting work, not retrieval-result caching.
- **Reject impossible supplemental pages earlier.** After source-map validation,
  a certified stable citation-header prefix can prove the token budget already
  exhausted, avoiding unnecessary source-unit projection and ranking. Packing
  order, source validation and final exact token counts remain unchanged.
- **Use a 4 MiB SQLite pager target per connection.** `PRAGMA cache_size=-4096`
  sets a connection-local KiB target. It is separate from the query-result cache,
  is not a hard process-memory limit and does not persist a file-format setting.

The derived index is added automatically to existing archives, including after
supported schema migrations, and SQLite maintains it for older/external writers.
Schema 3, source addresses, revision semantics, MCP response formats and product
dependencies remain unchanged. Q2 remains optional; its model and fusion policy
are unchanged. Development alternatives and adverse observations remain in the
[round-five record](https://github.com/Afloat16/AI-Memory-Book/blob/v0.3.3/docs/optimization-round5.md).

The index has storage and first-open costs. An earlier C3 probe of the same
index implementation recorded the following; logical content and revision were
unchanged. These observations retain their C3 source identity:

| Old archive | First open, v0.3.2 → C3, ms | Open + close, ms | Index allocation, bytes |
|---|---:|---:|---:|
| synthetic61 | 0.910 → 5.419 | 1.000 → 9.495 | 200,704 |
| public1015 | 0.844 → 4.502 | 0.930 → 7.791 | 151,552 |

Each source/cohort has one sequential observation with warm OS caches; these
are descriptive upgrade costs, not percentiles or a speed acceptance result.
Both copied archives reused free pages, so observed file growth was zero; the
allocated index space is still a cost. The recorded process high-water marks
cannot establish equal live RSS or zero memory overhead.

## Historical component strengths and limits

The prior supplied-page comparison at 1,024 `cl100k_base` tokens found default
Book complete evidence on **53.91%** of questions versus **44.53%** for
claude-mem 15.18.1 FTS, a **9.375 percentage-point** advantage. ai-memory v3.4.5
and the pinned billion-context kernel had higher recall and completeness;
billion-context also had lower search latency. The final-source C7 regression check
preserves Book's old default outputs. Competitors were not rerun, and old speed
ratios are not v0.3.3 measurements. Different component boundaries also prevent
a whole-product or all-dimensions superiority claim.

## Install or upgrade

Requires **Python 3.10+ with SQLite FTS5**. The registered publication channel is
a normal [GitHub v0.3.3 release](https://github.com/Afloat16/AI-Memory-Book/releases/tag/v0.3.3)
(`prerelease=false`), marked Latest on initial publication. Distribution is
through GitHub release assets, not PyPI. The installer uses the release wheel
with MCP/client extras in an isolated environment and preserves the archive.

**macOS / Linux**

```bash
curl -fsSLo install-memory-book.sh https://raw.githubusercontent.com/Afloat16/AI-Memory-Book/v0.3.3/scripts/install.sh
bash install-memory-book.sh
```

**Windows PowerShell**

```powershell
Invoke-WebRequest https://raw.githubusercontent.com/Afloat16/AI-Memory-Book/v0.3.3/scripts/install.py -OutFile install-memory-book.py
py -3 .\install-memory-book.py
```

Connect a client with `memory-book setup --client claude-code`, then run
`memory-book doctor` and restart the client. Add `--capture --background` to
setup when transcript capture is wanted. Use the installer's full launcher path
if needed. On upgrade, rerun setup with the existing database, clients and
capture options so MCP and any service point to the new environment; the prior
environment is retained. [Deployment and upgrade guide](https://github.com/Afloat16/AI-Memory-Book/blob/v0.3.3/docs/deployment.md#upgrading)
