# Open-source memory research for project and directory navigation

Research checked on **2026-11-16 (Asia/Shanghai)**. This is a source review and
adapter specification, not a new quality leaderboard. Repository snapshots below
are explicit commits; a source version string is not evidence of a published
release. Numerical claims require a separately frozen protocol and retained real
execution results.

## Precise positioning for AI-Memory-Book

The defensible engineering purpose is an **original-conversation archive that can
be browsed as a project book**: select the intended project, inspect its task or
chapter directory, read a page, and follow stable references to the original
session and turn. Bounded recall should recover the decision together with the
constraints and failed approaches that determine whether it applies.

This should be assessed through observable behavior: distinct exact project IDs,
discoverable directories, source coordinates that still identify the original
text, explicit handling of ambiguous scope, and evidence completeness within the
declared budget. A project filter supplied by an evaluator proves scoped retrieval
under that supplied filter. It does not by itself prove that a product selects
the right project, refuses an ambiguous request, or enforces multi-user access
control.

Several reviewed products already have local storage, source lookup, project
selectors or directories. ReMe is especially close to the proposed local file
navigation workflow. OpenViking has layered directory retrieval; Hindsight has a
wiki-like page hierarchy; Basic Memory has explicit directory and project tools.
Book's source-preserving, model-free default and conversation-specific hierarchy
are concrete design choices to test together. They are not proof of universally
better search, uniquely available folders, or stronger authorization.

## Additional real adapter: ReMe native BM25

### Upstream identity and installation

The pinned source declares `0.4.2.3`; that version was not available on PyPI when
checked, whose latest release was `0.4.2.2`. The adapter therefore runs the exact
source commit, not a package substituted by its version number. The official
35,157,379-byte source archive has SHA-256
`4b69c3bf3fee8b0061ada47aea61b45e4b8ae35f13ac0d1853d1cfdc61f11b15`.
Preparation additionally checks all 272 runtime files, the license and the
package metadata against Git blob identities from the pinned Git tree.

The [adapter lock](../benchmarks/competitors/reme-lock.json) records those files
and an independent CPython 3.12/Linux dependency profile. Its 130-package
[requirements file](../benchmarks/competitors/reme-requirements.txt) was resolved
from upstream base plus `[as]` dependencies with hashes. These packages are
separate from the previous comparison environment. SDK packages can be installed
without constructing or calling a model; the BM25 component creates no model or
embedding provider.

### Native input, ranking and scope

1. Store each supplied complete original page as its own UTF-8 `.txt` file. File
   paths encode the exact project ID and page ID by hashes, without case folding,
   punctuation removal or path-based project inference.
2. Call the official `DefaultFileChunker.chunk`, then pass its unchanged node and
   chunks to `LocalFileStore.upsert`. Keep the native 10,000-byte chunk size and
   100-byte overlap. Require exactly one chunk whose text equals the complete
   original page; reject a split or rewritten input instead of silently changing
   the protocol. The plain-text parser normalizes CRLF/CR, so non-normalized input
   would fail this equality check.
3. Call `LocalFileStore.keyword_search(query, limit, {"paths": exact_paths})`.
   Paths are selected only by the supplied exact project ID. The native store
   finds eligible chunk IDs before `BM25Index.retrieve_filtered` applies top-k.
   An unknown project supplies an empty exact-path set, not an omitted filter.
4. Keep the original query, native result order, default BM25 constants and native
   tokenizer/stopwords. Preserve the complete native result payload. Validate
   each returned path, chunk ID, line range and body against its original page;
   foreign or unmapped results are integrity failures, not silently removed hits.

This is an explicit supplied-file component mode. The default live application
watches Markdown in its memory directories; this adapter does not claim to test
that watcher, automatic memory evolution, Markdown authoring, link expansion or
the full client workflow. `DefaultFileChunker` is an upstream parser, not an
adapter-created chunker or replacement ranker. See its [implementation][reme-chunker]
and the native [file store][reme-store] and [BM25 index][reme-bm25].

Native Markdown parsing is a different registered mode: it renders an AST and
may prepend ancestor headings. Also, `include_frontmatter_in_metadata` is false
by default, so adding a project field to frontmatter alone does not enable a
chunk-metadata project filter. These behaviors must not be hidden by the adapter.

### Scope and lifecycle caveats

The Python application constructs a separate `ApplicationContext` for each
instance and binds its workspace at construction. Multiple embedded instances
need no separate HTTP listener. Reusing one workspace with native per-query exact
filters does not require a restart; switching the application's workspace is a
new-instance concern.

The lower-level native search filter is available through the Python job context
and file-store API. The default public search schema lists query, limits, tags
and dates, but does not expose every lower-level filter. Do not attribute a
Python-only component argument to every CLI/MCP/HTTP entry point without testing
that entry point. Native path-prefix matching uses string prefixes, so an exact
project boundary must use exact paths/metadata or a correctly delimited prefix.

The official `write` job writes a file; indexing is asynchronous in the full
application. `wait_for_paths` waits for file existence, not index readiness.
The component uses the upstream synchronous lifecycle around awaited chunking
and upsert calls. Its scope mapping is an evaluator-supplied project selection,
not native authentication or an ambiguity-refusal capability.

## Additional native capability track: official MCP memory

The pinned `@modelcontextprotocol/server-memory` package is `2.1.1` and requires
Node.js 24+. Use an explicit absolute `MEMORY_FILE_PATH` in an isolated state
directory. Entity creation can retain each supplied original as an observation;
`open_nodes` can retrieve the exact stored strings, and `read_graph` can verify
the graph and its relations. The server implements locking and atomic storage;
this source review is not a concurrency benchmark. [Package][mcp-package],
[storage guidance][mcp-readme] and [implementation][mcp-code].

`search_nodes` compares the entire query as a case-insensitive substring against
names, types and observation strings, then keeps matches in storage order.
Its `limit` is a count limit, not relevance ranking. `observationLimit` can provide
an overview before a full `open_nodes` read. `read_graph(entityTypes=...)` selects
types, while `search_nodes` has no equivalent scope argument at this pin.

A credible experiment can test real save/read/reopen behavior, literal lookup,
graph traversal and the consequences of using one graph versus separate
project-specific instances. If separate files/instances implement isolation,
record that deployment boundary explicitly. Do not add an adapter BM25 ranker,
split a natural-language query into custom keywords, or silently post-filter a
global result and call the outcome the server's native ranked retrieval.
Likewise, an empty literal result is not evidence of semantic abstention ability.

| Candidate | API key or external service needed for the proposed mode? | Honest experiment role |
|---|---|---|
| ReMe | No for the pinned local file/BM25 component; dependency installation and source download happen before offline execution | Additional relevance-ranked component with strict original-page/source validation |
| Official MCP memory | No model key; a local stdio server process and its JSONL file | Native graph, archive, literal lookup and source-read capability track |
| doobidoo MCP Memory Service | Local ONNX can avoid an external model service; requires a real model artifact and its proper dependency extra | Possible future local-model experiment; reject hash-embedding fallback rather than mislabeling it as real embedding execution |
| OpenViking | Documented full setup includes models and a server; local providers are possible | Feature review until its actual configured pipeline is run with retained evidence |
| Hindsight | Full ingestion/synthesis requires model execution and a supported database deployment | Feature review; existing-page reads alone do not represent the full memory pipeline |
| memvid | Official repository documents lexical BM25 without an API embedding provider | Existing family, not counted again; a further adapter needs its actual native scope/filter and package interface pinned and exercised |

No source review in this file creates a new precision, completeness, latency,
token-cost or coding-success result. A common ranked comparison and a product's
native project/directory workflow answer different questions and should retain
separate denominators and failure categories.
