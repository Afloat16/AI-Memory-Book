# 架构与数据语义

本文描述基于 v0.3.0 继续优化的当前开发版：保留原有精确词法索引，增加本地英语词形候选、完整原文片段优先的摘录和按实际页长度分配的上下文预算；分节策略不变。数据库新增派生索引并升级到 schema 3。当前验证与 v0.1 至 v0.3 的历史报告分开记录，见文末的证据边界。

## 目标

主要使用者是通过 MCP 调用工具的 AI agent。项目书、任务章、会话小节和证据页为记忆提供组织结构与地址；浏览器阅读器用于人主动检查源数据，不是 AI 读取记忆的前置步骤。

组织结构与读取执行顺序分开设计。目录解决“记忆在哪里”和“上下文怎样组织”；默认查询不需要模型逐层选择分支。一次 `recall_memory` 就返回相关原文、可寻址页 ID、来源和读取统计。只有当前任务依赖先前讨论时才需要检索，不要求每次用户提问都先加载目录或历史。

核心不生成答案，不调用 LLM，不把摘要当作原文，也不承诺所有语义改写都能被词法索引找到。

## 客户端、采集与运行进程

v0.2 将接入拆成两个独立能力：**MCP 读取**由客户端按需发起；**原生历史采集**由用户显式启用的本地 worker 执行。配置 MCP 不会自动读取客户端历史，也不保证模型在每轮提问前调用 recall 或自动注入上下文。

| 组件 | 职责与生命周期 |
|---|---|
| `setup` / `clients.py` | 为所选客户端合并 MCP 配置，并显示数据库和可选采集范围；不扫描会话正文 |
| `mcp` | 客户端启动的 stdio 子进程，按需调用本地存储；默认只读，`--allow-write` 才开放写入 |
| `sync --once` / `sync` | 对显式配置的来源执行一次增量同步或持续轮询，均不启动阅读服务 |
| `daemon` | 默认仅运行采集 worker，监测配置变化并重新加载；配置显式启用时才运行本地阅读服务 |
| 原生用户服务 | 用固定 Python 解释器和配置路径启动 daemon，由操作系统管理登录启动、停止和故障重启 |
| `serve` | 用户显式启动的可选本地阅读器，供人工检查目录和原文 |

MCP 初始化通过既有的 `instructions` 字段发送简短使用策略，v0.2.1 对该策略进行了细化。初始化不读取或注入全库目录、会话正文；策略要求已知项目时直接调用有预算的 `recall_memory`，仅在项目身份不明确时使用 `browse_projects`，仅在证据不足时继续读取选定页。分页浏览是可选工具，不是固定启动流程。默认连接只读；显式开放 `remember_session` 的连接还说明整会话替换语义，避免用片段覆盖完整记录。宿主是否向模型呈现说明、是否批准调用及模型何时调用工具仍由宿主和模型决定。完整使用约定见 [AI agent 操作指南](agent-guide.md)。

MCP stdio 子进程与采集 daemon 各自访问同一 SQLite 数据库。它们不通过 HTTP 互相调用，无需启动浏览器服务来连通 AI 与记忆。

CLI、MCP 与后台服务默认使用同一个用户数据目录。Linux 使用 XDG data 目录，macOS 使用用户 Application Support，Windows 使用 LocalAppData；`MEMORY_BOOK_HOME`、`MEMORY_BOOK_DB` 和显式 `--db` 支持独立部署。v0.1 工作目录下的 `.memory-book/memory.db` 不会自动搬迁，`doctor` 会提示可见的旧数据库。

安装器创建隔离的 Python 环境；安装本身不修改客户端配置、不启用采集、不创建登录服务。`setup` 的客户端配置更新先生成计划，支持 `--dry-run`，保留不相关设置、备份旧文件并在写前再次核对内容。JSONC 和无法安全合并的配置会返回手工片段；客户端自己的工具信任和权限提示仍由客户端决定。`--capture` 表示同意读取展示路径中的**已有及未来**受支持文本会话，`--background` 才进一步安装并启动用户服务。

Linux 的 `systemd --user`、macOS 的 LaunchAgent、Windows 的当前用户登录 Scheduled Task 都属于用户会话范围；不申请 root、不保存用户密码，也不默认开启退出登录后的永久运行。缺少可用用户服务管理器时，可自行监督 `daemon` 或执行一次同步。服务定义生成和测试通过不等于所有客户端版本、登录管理器和操作系统环境都已端到端验证。

## 显式采集与增量状态

采集配置包含数据库、manifest、可选日志路径、轮询间隔、阅读服务参数和来源列表。每个来源都声明目录、格式、匹配规则以及项目映射；只遍历这些目录，不自动搜索整台机器。默认轮询间隔为 5 秒。

v0.2.1 新配置以及缺少 `reader_enabled` 字段的配置默认使用 `false`，daemon 不监听 HTTP 端口。现有配置中显式的 `true` 或 `false` 保留；从 v0.2.0 升级不会悄悄改写原来的选择。需要人工阅读时可独立执行 `memory-book serve`，或在现有 daemon 配置中设置 `reader_enabled: true`；`reader_host` 和 `reader_port` 默认分别为 `127.0.0.1` 与 `8765`。`memory-book sync` 始终仅采集，即使配置为 daemon 启用了阅读器。

项目映射不能把不同工作区静默混为一谈：显式 `project` 绑定优先；有可靠 cwd 的原生会话按规范化工作区路径生成可读名称与哈希；缺少 cwd 的来源可按配置根目录下的工作区 bucket 分隔。`--workspace` 对记录的 cwd 做精确匹配。Gemini 与旧版 Kimi 的默认布局按目录 bucket 隔离；要仅采集其中一个工作区，选择该工作区的 `--source` 并指定 `--project`。在全局历史根目录设置一个显式项目会将选中的全部会话绑定到该项目，应结合较窄来源使用。

一次同步按以下顺序执行：

1. 对符合白名单规则的普通文件检查元数据；元数据未变则跳过正文读取。元数据变化后读取有大小上限的稳定快照并计算哈希，相同内容跳过解析与导入。
2. 解析受支持格式并映射成规范化会话。原生稳定 session ID 优先，缺失时 watcher 使用源文件路径派生稳定 ID，因此追加内容不会生成新会话。
3. JSONL 仅容忍末尾尚未换行的半条 JSON 或不完整 UTF-8 尾部；先导入完整前缀，后续追加再重试。完整的坏行会隔离该文件并保留先前成功导入的记忆，错误使用有上限的退避重试。
4. 先校验该文件全部规范化会话，再逐会话调用事务性替换。文件含多个会话时，原子性单位是会话；中途数据库失败后的重试保持幂等，不宣称整文件事务。
5. 原子更新 manifest。它记录文件签名、哈希、来源映射、会话身份、进度和错误代码，不保存会话正文。可选轮转日志只写事件、计数、来源标识和错误代码。

manifest 绑定数据库的规范化路径、持久化 `sync_generation` 和 revision。切换数据库、同路径重建数据库或恢复到更早 revision 时，旧跳过状态失效，现存来源重新导入。相同状态文件通过操作系统文件锁避免重复 worker。来源删除或 watch 移除不会删除已归档记忆；失效来源会释放身份占用，允许重新添加。两个仍有效的文件声称同一个项目/会话身份时报告冲突，避免悄悄覆盖。

默认单文件上限为 64 MiB。采集跳过选定树内的符号链接、数据库与状态文件、已知凭据/配置文件名以及非会话内容；这些过滤不是秘密检测器，合法会话正文中出现的密钥仍会被存储。状态、日志与数据库路径可分别配置，不能互相覆盖。

daemon 监测配置文件的元数据变化，先停止旧 worker 和阅读服务，再加载新配置。缩小范围或移除来源会在当前文件处理结束后生效；无效或被删除的配置会停止旧采集范围，而非继续沿用旧权限。停止信号也在文件之间检查，空闲等待可以立即唤醒。直接调用 Python `watch(config)` 使用给定配置快照，文件热加载由 `run_daemon` 负责。

### 原生格式支持边界

原生采集支持已验证的 Claude Code JSONL、Codex rollout JSONL、Gemini 会话 JSON/JSONL，以及旧版 Python Kimi 的活动 `context.jsonl`。Gemini JSONL 会按记录顺序重放 `$set`、`$patch`、`$rewindTo`，再提取当前可见文本，避免把已撤销内容当作当前会话。旧版 Kimi 跳过 checkpoint、usage、system-prompt 和 think 记录，不读取轮转旧文件。

当前 Kimi Code 的 `~/.kimi-code` 与旧版 `~/.kimi` 是不同格式；本版本只提供当前 Kimi 的 MCP 配置，不把 session index 当作会话正文。更多 MCP 客户端能读取同一数据库，但不因此获得原生历史采集适配器。适配器只保留所支持的可见文本，不声称完整保存多模态附件、工具调用结构或宿主内部状态。官方格式依据见[研究记录](research.md)，具体接入见[客户端集成](integrations.md)。

## 写入路径

1. 校验一条规范化会话：项目、稳定会话 ID、可选任务 ID、来源时间和文本消息。
2. 在用户消息边界组装 turn；一个 turn 包含一次用户提问及下一次用户提问之前的回答/文本工具消息。前置 system/developer 消息保存在源 JSON 中，不自动变成检索指令。
3. 自适应分节根据长度、问题词面相似度和常见追问开头分组，最多合并四个 turn。超过页上限的单个 turn 按段落/换行优先切分，必要时硬切，不丢弃字符。
4. 在一个 SQLite 写事务中保存规范化源会话、turn、section、page、精确与词形两套 FTS 索引和抽取式目录概览。两套索引复用同一份规范化索引文本；词干化由 SQLite 内置 tokenizer 执行。
5. 递增全库 revision，删除旧查询缓存。任何索引写入失败会回滚源会话与派生记录。

默认参数是 `max_page_chars=900`、`min_page_chars=400`、`similarity_threshold=0.12`。这些是开发集选择的工程参数，不是语言学意义上的正确章节边界。小于下限的相邻短问答可能合并；较长文本遇到话题变化则分开。默认配置可以通过 Python API 调整，CLI 暴露模式和页上限。

## 数据对象

| 表 | 用途 |
|---|---|
| `projects` | 显式项目 namespace 和显示名 |
| `chapters` | 项目内的显式任务，或没有任务 ID 时的独立会话章 |
| `sessions` | 规范化源 JSON、来源/导入时间、内容哈希、分节配置 |
| `turns` | 提问与后续消息的完整文本，以及原消息编号 |
| `sections` | 连续问答分组和抽取式问题概览 |
| `pages` | 内容相关地址、页正文和精确来源区间 |
| `pages_fts` | 预分词后的标题、问题提示、正文和目录名称，使用 `unicode61` 精确词项索引 |
| `pages_stem_fts` | 相同索引文本的 `porter unicode61` 派生索引，用于英语词形匹配 |
| `recall_cache` | 查询参数哈希、revision、序列化结果和有限缓存条目 |
| `meta` | 全局 revision，以及采集状态使用的数据库 generation 标识 |

数据库带 SQLite `application_id` 和 `user_version`。v0.1 至 v0.3 使用 schema 2；当前开发版使用 schema 3，新增 `pages_stem_fts` 及其删除触发器，不改变源表字段、分节规则或页地址的计算方式。首次打开旧库时自动升级：取得 `BEGIN IMMEDIATE` 写锁后重新检查版本，避免两个进程根据旧版本重复升级；schema 1 先补齐旧字段并重建精确索引，再与 schema 2 一样创建词形索引。整个升级在同一事务中完成，失败时回滚。成功后递增一次 revision 并清空旧查询缓存；后续打开不会重复回填。

schema 2 的升级直接复制已有 `pages_fts` 中的规范化文本，让 SQLite 建立词形索引；原会话 JSON、页 ID、页正文、来源区间、已有精确索引和自定义分页设置保持不变，不需要重新导入会话。早期开发 schema 1 的迁移仍会补齐缺失的源时间和设置：它未保存自定义分页上限，升级保留实际已有页，后续 link 使用当时的默认上限 1800；若原来使用了自定义参数，应按原参数重新导入。

升级后需重启旧版 MCP 进程和采集 worker，统一使用新版本。已经打开的旧连接若在升级之后完成写入，数据库级 revision 触发器会在同一写事务内从精确索引重建词形索引，避免新增页或目录修改只进入其中一份索引。新版写入先同步两份索引并更新 `stem_revision`，正常路径不触发全量重建；旧连接兼容路径的额外成本随索引大小增长。本轮早期缺少此保护的 schema 3 开发库也会补装保护并回填一次。

v0.1 至 v0.3 历史版本不能重新打开 schema 3 数据库，当前没有自动降级路径；需要回退时应恢复升级前备份。新版本拒绝不支持的 schema 或其他应用的数据库。FTS5 及内置 Porter tokenizer 是运行前提，不会悄悄改用全表扫描；新增索引的首次构建、后续写入和磁盘空间属于需要单独测量的成本。

`project + session_id` 决定源会话身份。无 `created_at` 时首次写入产生的时间会进入源 JSON，后续导入和导出保持该时间。用户显式提供的项目名/任务名可以更新显示名；省略名称不会把已有友好名称覆盖成 ID。

跨会话任务使用显式 `task_id`。`link_session` 调整任务归属时复用原分节配置；未改变的页正文和页地址保持一致。会话替换、任务目录改名和 link 都在同一写事务中同步两套索引。当前不是自动跨会话语义聚类系统。

## 读取路径

FTS5 使用预分词文本：英文/标识符拆词、Unicode 正规化和重音折叠、中文连续字符 bigram。两套索引接收相同文本，`pages_stem_fts` 额外应用 SQLite 的英语 Porter 词干化，使部分词形变化也可成为候选。它不提供同义词知识、跨语言语义匹配或多跳事实推理，词形匹配也可能产生过宽命中，因此保留精确路由并给它更高的融合权重。查询里的 FTS 操作符不会直接执行，SQL 参数也不会拼接用户值。

检索按以下顺序完成：

1. 用完整查询参数、索引版本、检索版本和 revision 检查有界持久化缓存。检索版本独立失效，不要求仅因摘录或排序变化重新导入原文。
2. 在同一个读快照中执行 FTS BM25，项目/章节/会话过滤在每一路候选截断前生效。每一路都要求其正文索引命中，只有目录名命中不能被当作证据。
3. `flat` 始终只查询精确索引，保持原 BM25 路径。默认 `book` 仅在规范化查询词含 ASCII 字母时增加词形路由；纯中文查询不增加检索路数。每路最多取 96 个候选，双路按页 ID 合并后最多 192 个，最终返回仍受 `limit` 和字符预算约束。
4. 两路的有序页 ID 完全相同时，保留原精确 BM25 分数，避免重复观察同一排名改变后续互补性选择。否则保留每一路的分数差距：令 `E = max(0, -bm25_exact)`、`S = max(0, -bm25_stem)`，按各自候选中的最大值归一化后使用 `2 × E / max(E) + S / max(S)`。缺席路由贡献 0，空路由或最大值为 0 时分母取 1；精确与词形路由权重固定为 2:1。该规则不只看名次，但也不保证每个查询都优于单路检索；开发比较与逐查询损失检查记录在 `benchmarks/experiments/score-aware-fusion-selection.json`。
5. 目录元数据在候选截断后加载，双路共用候选只加载一次。`book` 沿用最高 15% 的目录标题重叠加权；融合后的分数相同时，依次用精确名次、词形名次和页 ID 确定顺序，不硬裁剪其他章节。
6. 在排名靠前的至多 `4 × limit` 个候选中，沿用已有索引词的有界互补性重排，保留第一名并减少重复命中挤掉其他问题要点的情况。显式询问当前/最终状态时，仅在同章且非空精确匹配词集合相同的候选间优先较新会话；历史、明确年份和时间限定查询不使用此规则。仅有词形命中的空精确匹配集合不被当作等价修订。
7. 一次 SQL 批量加载最终选中页的原文、来源和展示字段，预留引用开销后按实际页长度分配正文预算。对双路检索中实际需要截断的最终页，在同一读快照内批量读取词形索引的 `highlight`，为每页提取至多 64 个去重匹配词形并加入摘录定位词；完整页不需要这次额外读取。标记来自规范化索引文本，仅用于定位，返回内容仍从原文截取。
8. 在字符预算内选择一个原文窗口。先比较不同查询词的覆盖数，再比较完整来源行/句子覆盖的查询词数，最后才用重复词频、匹配位置和起点打破平局。重复关键词片段不能仅凭出现次数挤掉覆盖相同查询词的完整事实；较长行使用句子边界，这些边界不改写或合成原文。引用头保留页 ID、项目、会话和时间，完整层级标题保留在结果元数据与页面读取中。
9. 写缓存前再次核对 revision，避免并发导入后把旧结果重新写回缓存。

`flat` 与 `book` 在当前开发版中的差异包括词形候选、目录加权和互补性/当前状态排序，不能把二者的整体差异单独归因于目录结构。词形路由与目录结构的质量、耗时和 token 效果都需要在固定数据与预算下比较。BM25、Porter tokenizer 和 `highlight` 的机制见 [SQLite FTS5 官方文档](https://www.sqlite.org/fts5.html)。

## 来源字段

返回结果的 `source_refs` 指向**原始规范化会话**，而不是摘要猜测出的出处。以下是 Python API、CLI、页面读取以及 `recall_memory(details=true)` 的完整字段；v0.3 默认 MCP recall 只发送 `project`、`session_id`、`turn_index`，需要精确位置时按需请求详细数据。

| 字段 | 语义 |
|---|---|
| `project` | 原项目 ID |
| `session_id` | 外部稳定会话 ID |
| `turn_index` | 从 0 开始的用户提问/turn 编号 |
| `message_indices` | 源 `messages` 数组的消息编号 |
| `start`, `end` | 本次返回内容在完整页正文中的半开字符区间 |
| `turn_start`, `turn_end` | 同一段在组装后的完整 turn 文本中的半开字符区间 |
| `created_at` | 源会话时间 |

turn 文本包含 `USER:`、`ASSISTANT:` 等角色标签，区间基于这个可重建的文本。不是原 JSON 文件字节偏移。`excerpt_spans` 表示摘录对应的页区间；显示省略号不属于原文区间。

页 ID 包含来源身份、位置与正文哈希。修改正文后旧页地址失效，读取返回 not found，不会静默把旧引用解释为新内容。原始规范化会话可通过 `get_session`、CLI `source` 或 JSON 导出恢复。

## 预算与分页

`context_chars == len(context) <= budget_chars`。这里使用 Python Unicode 字符计数，不是 UTF-8 字节数。引用标题和来源时间算入 context。较小预算可能连一个包含出处的证据块都容纳不下，此时返回空 context 和原因。

预算分配先为可容纳的排名前缀预留引用头、分隔符和有用的正文空间，再按页实际长度分配正文额度：较短页不需要的额度会返还给较长页，包括排名更靠前的长页。全部选中原文与引用能放入预算时，完整保留这些页；需要截断时共享剩余空间，避免前排已经截短、后排却留下未用额度。很小的预算优先保留一个有出处的片段，可能返回少于 `limit` 个结果。预算分配不读取答案标注，也不改变候选的证据顺序。

Python API 返回 `context` 和结构化 `results`，便于应用渲染。MCP 返回无缩进的单份 JSON 文本，去掉 `results` 中重复的证据文本与路径，不同时发送 `structuredContent`。默认 recall 还省略精确坐标和日常诊断；`details=true` 恢复这些字段，证据正文保持一致。所有 MCP 工具统一为一个 JSON 文本块，项目列表在该块中是 JSON 数组。来源 JSON 等元数据仍会增加响应体积，所以不能把 context 预算写成整个模型输入的精确上限。

目录的章、节、页分别分页：`toc`、`chapter`、`section`。章节中每个小节默认只预览 20 页，剩余页通过 `pages_next_offset` 继续。正文 `read` 也支持字符偏移分页。Markdown 导出会遍历全部分页。

## 缓存、并发与删除

缓存默认最多 128 条，全库 revision 失效机制优先保证正确性；一个项目更新也会清掉其他项目的缓存，这是简单性和缓存命中率的取舍。检索版本也进入缓存键，schema 升级会清空旧缓存。当前淘汰按写入时间，不声称是精确 LRU。

SQLite WAL 和 busy timeout 支持多个本地连接。一个 `MemoryBook` 实例不跨线程共享；网页请求使用独立连接。MCP 在一次 transport lifespan 内惰性建立并复用同线程连接，退出时关闭；无 lifespan 的直接 SDK 调用、其他线程和无法可靠辨认文件身份的环境使用临时连接。每次借用前检查数据库设备/文件身份，文件替换后重新打开。外部 writer 的正常写入仍由读快照和 revision 校验保证可见性。源会话更新采用整会话替换事务，而非只重建单个追加 turn，因此非常长的会话频繁重复导入仍有写入成本。

目录词集合另有最多 512 项的连接内缓存，按完整目录文本作为 key，值为不可变集合；重命名使用新 key，关闭连接时清空。它缓存的是分词结果，不是查询答案，与最多 128 条的持久化结果缓存不同。

删除会话/项目时，外键级联移除派生行，页删除触发器分别移除精确索引与词形索引，再同步清空缓存。CLI 删除要求明确 `--yes`；默认 MCP 只读，也没有 MCP 删除工具。删除不提供内建回收站，应先导出需要保留的数据。

## 运行边界

用户显式启动的本地阅读服务默认只允许 loopback 地址，校验 Host；写入额外要求同源 Origin 和每启动随机 token。页面只用文本节点展示历史内容，不执行其中的 HTML。容器镜像默认运行 stdio MCP，不监听 HTTP；可选阅读器在容器内绑定 `0.0.0.0` 必须额外显式传入 `--container-bind`。随仓库提供的 Compose reader 仅发布 `127.0.0.1:8765:8765`，Host/Origin 检查仍只接受本机地址。这个容器选项没有增加身份认证、项目访问控制或 TLS，不可作为公网多用户部署方案。容器默认也不能读取宿主会话，采集需要额外显式挂载和配置。

数据库保存规范化源文本和查询缓存，均为未加密本地数据；状态中的路径、来源身份与哈希同样可能敏感。日志不写入会话正文，但不等于所有本地文件都无敏感信息。采集、索引和检索不调用外部模型；MCP 宿主仍可能把返回证据发送给其模型服务。详见[安全边界](../SECURITY.md)。

历史中互相矛盾的决定不会自动合成“唯一真相”。最新状态类查询会提示检查来源时间。低词面重叠、隐含关系或需要外部知识的问题是当前词法版本的明确边界。下一阶段可研究可选语义候选与事实版本关系，但必须保留原文兜底和对照实验。

## 性能证据的版本范围

当前开发版的评测入口是[检索质量与预算报告](../benchmarks/RESULTS-recall-quality.md)。词形候选、摘录和预算分配属于实际行为变化，不能只凭算法名称或单项回归测试宣称达到同类产品的回答质量；新增索引的升级与写入成本也不能从查询延迟中省略。具体结论应以该报告冻结的代码、数据划分、实际返回证据、token 计数和计时边界为准。

下列 v0.1 至 v0.3 报告是各自代码版本的历史证据，不代表当前开发版已经复现同样结果，也不作为当前实现的性能保证。

[v0.3.0 实测](../benchmarks/RESULTS-v0.3.0.md)将当时旧版/新版核心检索、真实 MCP 调用、公开 LoCoMo 语料及外部原生检索组件分开比较。真实 MCP 返回 token 使用两个明确的参考 tokenizer 计数；包含元数据、初始化和调用边界说明。公开语料是独立发布的 persona-agent 对话数据，不能当成用户私人历史或大模型端到端回答准确率。当时新版的退步、仍失败的问题类型和未测项目也保留在报告中。

[v0.1 实验记录](../benchmarks/EXPERIMENTS.md)比较同一词法引擎下的 session、turn、adaptive 分节和 flat/book 排序。两个未参与参数选择的合成 heldout seed，在 8,000 字符预算下 adaptive 的证据召回均为 77.27%、完整证据率均为 78.95%，本地未启用结果缓存的 p95 为 7.42–7.46 ms。目录重排序没有带来 aggregate 召回提升，低词面重叠改写和远处双事实查询仍失败；不能据此推广为真实问答或竞品性能结论。

这些计时排除进程启动、后台扫描/导入、MCP 传输、网络与模型推理，且保留 SQLite/操作系统页缓存。v0.2 沿用原报告及源版本记录作为历史证据，没有将新增采集功能的延迟、资源占用或多客户端实际体验补算进旧成绩。

另有独立的 [v0.2.0 采集 smoke 测量](../benchmarks/reports/capture-v0.2.0.json)，以固定的 300 个小型合成会话验证首次导入、8 次无变化扫描及单文件更新。它记录本机 `sync_once` 墙钟耗时与实际计数，不测量常驻 daemon 的 CPU、内存或电量，也不能外推其他设备或规模。无变化时零导入不等于零磁盘写入。v0.2.1 的默认值与说明调整没有重写这些历史测量，后台运行也不构成零开销承诺。
