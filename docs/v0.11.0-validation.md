# v0.11: directory addresses and current engineering evidence

This development record distinguishes product contracts, unchanged-fixture
quality, new component executions and diagnostic probes. No result here
establishes universal superiority, coding-model accuracy or production task
completion. Earlier attempts and their exact source identities are retained.

## Product scope

Projects are books, tasks are chapters, related questions are sections, and
original evidence is readable by page. Similar repositories can reuse symbols,
session names and task names while remaining in explicit project namespaces.
Project binding prevents accidental scope changes within that connection; it
is not a multi-user authorization boundary or automatic workspace detection.

`search_directory` adds a missing first step: find chapter addresses from
indexed `title`, `question` and `directory` metadata even when body text does
not repeat those headings. The implementation groups hits before paginating
chapters and returns at most five matching section previews per chapter.
Each chapter uses its best matching metadata page's lexical rank. Matching
any analyzed query term can return a directory; this is OR matching, not a
semantic answer guarantee or an exact-phrase lookup.

Python `MemoryBook.search_directory`, CLI `locate`, MCP `search_directory`
and HTTP `/api/locate` expose the same locator. Optional project/chapter
constraints are validated before searching; unknown or conflicting scopes do
not widen the search. MCP inherits a bound connection's project on every call.
Results explicitly identify themselves as `result_type="directory"` and
`evidence=false`. Titles and extractive summaries are navigation hints. Follow
their actual IDs to original pages before citing factual statements.

Each `toc`, section or locator request reads its metadata and counts in one
snapshot, while preserving a caller-owned transaction. `toc` and the locator
also read their reported revision in that snapshot; section responses do not
include a revision field. Separate requests may observe later archive states
during capture; no multi-call snapshot is promised.

## Current revision recovery

The old current-state route could lose a brief later correction at either the
96-match FTS cutoff or the `4 × limit` reranking pool. The new route supplements
chapters that the original relevance pool already reached with recent lexical
candidates. Scope applies before SQL `LIMIT`. Chapters share a maximum of 96
additional returned candidates; within a session, later section/page order
breaks otherwise equal creation times.

Previously unseen pages start with no relevance score; already ranked FTS-tail
pages retain their original relevance. Every supplementary pool member must
qualify before promotion through authenticated comparable declarations and chapter,
field and remaining-query-facet rules. This mechanism cannot infer authority
from a date or prove that a newer statement is factually correct. The recall
cache version increases from 16 to 19; archive schema 4 and source IDs remain.

Every page admitted to declaration comparison is independently checked against its complete
original turn. For byte-identical bodies, only pure declaration/quoted-text
parsing is reused within that call. Source authentication is never reused
between pages. Custom source readers retain the conservative path.

### Retained review blockers

An independent review reproduced a candidate-2 regression after the above
probes: a recent agenda with matching terms but no declared decision could
inherit an older decision's score through a fallback exact-term group. This
blocked candidate 2. Its [complete baseline/candidate responses](../benchmarks/reports/v0.11-development/unclassified-proposal-review-attempt1/)
and [additional failing tests](../benchmarks/reports/v0.11-development/proposal-qualification-candidate2-failures.log)
are retained. Candidate 3 qualifies all added members before score changes or
same-body deduplication, including metadata already present in the FTS set but
outside the original reranking pool. It preserves rejected tail entries and
rechecks grouping after rejection so disallowed fields cannot alter remaining
query facets. The original pool's fallback behavior remains intact.

Candidate 3 passed 109 focused native tests and 108 Python-reference tests;
one existing native-specific comparison is explicitly skipped when native mode
is disabled, and passes in the native run. The first independent review found the prior proposal qualification issues
resolved, but a subsequent adversarial check found another blocker: a
`Staging lease_duration=99` declaration inherited the `production` query facet
from a separate sentence on the same page. The no-expansion control retained
`Production lease_duration=30`. Candidate 3 is therefore also **blocked from
release** pending statement-local facet qualification for added proposals and
their anchors. Its source, successful checks and failing control responses remain
separate; final committed-source replay and delivery gates still apply. Passing the six original configurations did not establish
correctness on these additional cases.

Candidate 4 conservatively associates remaining query facets with the
individual field declaration. Both an added proposal and its original-pool
anchor must contain one simple declaration per field with the exact remaining
query terms as its adjacent qualifier. Other sentences, user questions, other
fields, ambiguous repeated declarations and unparsed suffixes cannot supply
that qualifier. The [candidate-4 report](../benchmarks/reports/v0.11-development/candidate4-declaration-facets.md)
retains the candidate-3 failing tests, candidate-4 focused tests and the extra
source-check/reanalysis cost.

The final candidate-4 snapshot reran both unchanged review scripts. The agenda
cases with 8/120 older sessions and the cross-sentence qualifier cases with
8/104 older sessions all retained the recorded decision. Candidate results,
context and candidate count matched their baseline controls; complete original
page follow-ups and both source inventories were independently checked.
[Agenda verification](../benchmarks/reports/v0.11-development/unclassified-proposal-review-attempt2/verification.json)
and [facet verification](../benchmarks/reports/v0.11-development/facet-association-review-attempt2/verification.json)
retain all eight baseline/candidate responses. These four authored candidate
configurations do not remove the original-pool limitation below.

### Remaining model limits

Only already relevant chapters are expanded. “Exact” means the existing
non-stem lexical index, not complete-phrase matching. More than 96 newer but
incomparable matching records can still hide a useful earlier revision.
Cross-session ordering uses the stored `created_at`; unrecorded real decision
times cannot be reconstructed. Field syntax and chronology do not establish
source authority, conflict resolution, completeness or abstention.

The supplemental admission checks do not change the original comparison
pool's fallback ordering. A recent agenda or mixed-context statement already
inside that pool can still rank ahead of an earlier decision. The qualification
rule is intentionally narrow: complex but valid prose can be left outside the
extended pool. It is not a global declaration-truth or query-context validator.

## Additional real upstream components

The preregistered extension runs Haystack 3.5.0 `InMemoryBM25Retriever`,
BM25S 0.3.16 native defaults, and Memvid SDK 2.0.160 explicit lexical mode.
It uses the unchanged 80 questions, currently visible original pages, exact
project scope, at most five native candidates and the original shared
whole-block packer. All 43 dependency versions and wheel hashes are pinned.
The fixture materializer is the immutable v0.10 baseline; it does not execute
Book recall. Backends receive supplied pages and queries, without gold labels.

The first complete attempt contains 18 successful setups, 720 native calls
(80 questions × three backends × three repetitions), and 480 packed responses
(80 questions × three backends × two budgets). Repeated calls are stability
observations, not additional quality cases. The independent offline audit
recomputes the complete row inventory, request labels, whole native mappings,
source and budget checks, every score and all aggregate/category summaries.

|---|---:|---:|---:|---:|---:|---:|
| BM25S, retrieval library | 2,400 | 80/80 | 72/72 | 48/48 | 0 | 1,846.7 |
| Haystack BM25, framework component | 2,400 | 74/80 | 66/72 | 42/48 | 0 | 1,884.7 |
| BM25S, retrieval library | 1,200 | 80/80 | 72/72 | 48/48 | 0 | 1,045.3 |
| Haystack BM25, framework component | 1,200 | 74/80 | 66/72 | 42/48 | 0 | 969.9 |

**BM25S ties Book's complete evidence and policy counts at 2,400 characters
and exceeds Book's common-block counts at 1,200.** The data therefore does not
support a claim that Book beats every lexical component or every question.
Haystack/BM25S are framework/library components, not complete memory products.

Memvid's formal native responses contain empty hit lists for every original
question. The adapter did not discard candidates. This configured
result is retained, but is not used as a zero-score product ranking. A separate
[14-call diagnostic](../benchmarks/reports/v0.11-extended-lexical/memvid-query-diagnostic-1/report.json)
retrieves fully verified pages for original-text keyword controls, while the
full question remains empty with or without scope. This establishes a working
index and a query/configuration boundary, not every internal matcher rule.
Diagnostic queries do not replace original questions or overwrite the formal attempt.

Memvid also requires a disclosed source-mapping boundary: native lexical text
normalizes whitespace and adds framing, and its text-only API probe returned
an empty blob. Before recovering original whitespace for the common packer,
the adapter checks native frame identity, URI, scope, title, timestamp and the
entire normalized body plus known framing. This is validated supplied-page
mapping, not evidence of byte-exact native source reading or native citations.
The exact published wheel has one inconsistent internal RECORD entry; the
installed extension is instead checked against the pinned official PyPI wheel
and its actual archive member. Original failures and hashes are retained.

## Test and delivery provenance

The first full development suite failed. It initially lacked historical
report files excluded by sparse checkout, and ran while sources were changing,
so source-bound checks correctly rejected the run. The complete original log
and counts remain in [the failed-attempt record](../benchmarks/reports/v0.11-development/environment/candidate-tests-attempt1.json).

Historical audit fixtures now read hash-verified original source bytes instead
of accidentally substituting the new runtime. Their production evaluators,
registered hashes and acceptance criteria remain unchanged. A synthetic host
fixture now consistently uses synthetic paths. MCP 1.29 correctly takes the
official fallback because the existing production fast-path guard authenticates
1.30 only; live real-SDK tests cover automatic/fallback/explicit-helper output
equivalence without widening that guard. The 35 focused tests passed, with the
intermediate failed fix preserved in [the compatibility record](../benchmarks/reports/v0.11-development/historical-sdk-compatibility.md).

The later immutable candidate-3 suite ran 1,579 tests with 12 errors caused by
missing historical files and the real MCP child's tokenizer cache environment.
Its [original failed log and environment record](../benchmarks/reports/v0.11-development/environment/checkpoint-tests-attempt2.json)
remain. The checkout and explicit verified cache were corrected; all 16 affected
checks then passed without changing production logic or acceptance criteria.

The complete final candidate-4 suite on commit `6619724` ran **1,603 tests**:
**1,589 passed, 14 skipped, zero failures or errors**. Two skips require Windows
and twelve require optional PyArrow; they are not counted as passes. Source and
native binary hashes matched before and after execution. The
[complete log, command, environment and identities](../benchmarks/reports/v0.11-development/environment/final-tests-attempt1.json)
are retained.
