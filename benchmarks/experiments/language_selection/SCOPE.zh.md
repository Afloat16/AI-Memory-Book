# 语言对照实验的解释范围

本轮比较的是具体执行方案在固定项目、语料和接口边界下的表现。候选与运行器冻结在
[`40a8ce42`](https://github.com/Afloat16/AI-Memory-Book/tree/40a8ce42b4131b511dcacd446d175b878b74a6f8/benchmarks/experiments/language_selection)，
产品基线为 `234891619d7bed88ddf3fae37e7f3e1b14a808b6`。
本文不包含性能结论；采用结论必须另有完整正式测量、输出审计和 A/A 对照支持。

## 候选与可以回答的问题

| 候选 | 实际执行边界 | 可以回答的问题 |
| --- | --- | --- |
| current | Python 主体、现有 22 个 C 入口、SQLite | 其他候选相对当前实现是否有收益 |
| rust_same | 同一 CPython 接口下，将其中六个 C 函数改用 Rust | 这六个具体实现的 C/Rust 差异 |
| c_table / rust_table | 相同 Unicode 映射表、共同守卫和两遍分配策略 | 共享表策略是否有效；C/Rust 同策略对照结果 |
| c_window / rust_window | 原生数据结构持有完整选窗计算阶段，使用共同适配器 | 扩大执行边界是否有效；C/Rust 同边界对照结果 |
| c_metadata / rust_metadata | 完整有界候选元数据方法，保留原 SQL 和原地更新语义 | 一个有实质占比的 Python 方法迁移后的端到端效果 |
| node_window | Python 将选窗任务交给常驻 Node 子进程 | 当前桥接方案的完整阶段成本 |
| node_small | 三个小接口通过常驻 Node 调用 | 当前桥接方案的小接口成本 |

TypeScript 另有类型擦除和执行函数身份检查。Shell 另有两个 ASCII 内核的 Bash 等价性、RPC、批量摊销和冷启动诊断；两者不冒充新增完整检索候选。

候选接入见 [experiment.py](experiment.py)，构建和冻结规则见 [host.py](host.py)，
配对和采用规则见 [analyze.py](analyze.py)。比较仍包含具体编译器、优化选项、库、分配和守卫的影响；没有脱离实现的“语言倍数”。

## 两个完整阶段的边界

| 阶段 | 包含 | 阶段外保留的工作 |
| --- | --- | --- |
| 选窗 | 从准备好的文本、词项、位置和宽度开始，完成证据单元、候选窗、命中频次、评分、稳定决胜、选窗与原文坐标渲染 | 查询分词、归一化、来源折叠、字面命中查找、数据库检索、整体预算和响应组装 |
| 候选元数据 | 原方法守卫、相关度界限、保留集合、carried metadata 活视图或 light 查询、目录请求与查询、验证、原字典更新及有序返回 | 初始 FTS 查询、完整候选融合、后续排名及新颖性选择、正文、摘录、来源与最终响应组装 |

元数据方法本身包含原有数据库调用：进入剪枝路径后，carried 路径保留目录查询，普通字典路径保留 light 与目录两条查询。它继续使用 Python SQLite 接口和 CPython 容器，并非 Rust 自有数据的完整检索流水线。

两个阶段都有明确的普通输入域和兼容路径。实际覆盖必须结合 native 完成、入口回退及 Python 后半段接续计数判断，不能只看扩展是否加载。

## Rust 的 FFI 与 GIL

本轮 Rust 扩展使用 unsafe CPython FFI、Python 原始指针和引用计数；没有新增释放 GIL 或并行执行设计。选窗内部使用 Rust 数据结构，元数据方法仍广泛操作 Python 字典、集合和 SQLite 行对象。

因此，本轮可以验证 Rust 在既有 CPython 应用中的扩展及完整处理阶段，不能证明移除 CPython、消除 GIL 或完整安全 Rust 对象模型的效果。实现可核对 [六接口](rust/src/lib.rs)、[选窗](rust/src/window.rs)和[元数据](rust_metadata/src/lib.rs)。

## Node 内核和实际桥接

正式 Node 候选包含 JSON 编解码、管道收发及 Python 结果重建。补充的 Node 内核诊断排除了这些成本，必须分列。完整 Node 应用尚未实现或测量。

桥接候选变慢不能排除全 Node 应用；内部内核变快也不能直接换算成完整应用收益。Shell 的批量指标仍包含协议成本；TypeScript 检查仅针对本实验的类型外观层，不代表所有 TypeScript 程序的运行行为。

## 仍未迁移的边界

| 范围 | 本轮状态 |
| --- | --- |
| 完整 recall 路由、候选融合、正文与响应组装 | 只替换所列阶段 |
| 完整 index_text / identifier_terms / terms 流水线 | 只替换部分内核，未迁移整串规范化与跨字符重排 |
| 确定性 JSON、ID/哈希、来源组装 | 保留现有实现，其中也包含已有原生库成本 |
| Python SQLite 驱动与行对象物化 | 十候选全部保留 |
| token 预算组织 | 进入端到端验证，未完整迁移组织逻辑 |
| 可选语义检索、模型编排 | 没有完整路径的语言对照 |
| MCP 主体、CLI、采集器、HTTP 层 | 没有独立 Rust 或 Node 服务原型 |
| 多核与并发架构 | 本轮不作对应性能结论 |

## 数据解释约束

- 以当前 C/Python 为采用基线；纯 Python 仅用于输出参考，不能把相对旧纯 Python 的收益写成当前版本的新增收益。
- 共享表与扩大原生执行阶段改变了数据或调用组织；必须同时看 C 控制组，不能将全部收益归于 Rust。
- 普通语料与 Unicode 压力语料分列。完整结果包含不利值、失败尝试、启动及进程资源。
- 正式统计以六个完整轮次的成对差异为单位；不把相关的查询当作独立统计样本。各场景区间未作多目标搜索的多重比较校正。
- 表中的合并 p50/p95 是描述值，采用门槛使用成对轮次指标，两者不可混用。
- 当前实验来自一组固定 Linux x86-64 环境，不能直接推广到 Windows、macOS、其他硬件或不同语料分布。
- 审计通过说明已注册案例的等价性，不是对所有可能输入的数学证明。
- 最终可选择“已验证候选中适合当前工作负载的实现”；本轮既不证明某语言全局最快，也不证明完整 Rust/Node 迁移没有潜力。
