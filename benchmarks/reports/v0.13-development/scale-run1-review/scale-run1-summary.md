## 正确性结果与完整失败

下表为每个版本各自的 7 阶段汇总，两版本逐条 score 与 evidence projection 完全相同。

| 指标 | 基线 | 候选 | 含义 |
|---|---:|---:|---|
| recall 完整证据 | 336 / 392 可回答配置 | 336 / 392 | 85.71%，不包含无证据查询 |
| recall 必需证据片段 | 392 / 448 | 392 / 448 | 87.50%，多来源题每题需要两段 |
| recall 当前来源排首位 | 80 / 168 适用配置 | 80 / 168 | 47.62%，不能用完整证据率代替 |
| 旧来源先于当前来源 | 32 | 32 | 前四检查点的 8 个英文 current 查询 |
| 目录追读完整证据 | 56 / 56 | 56 / 56 | 每检查点 8 个配置 |
| 目录追读当前来源排首位 | 56 / 56 | 56 / 56 | 全导航链的最终原文证据 |
| 无证据查询仍返回非空上下文 | 56 / 56 | 56 / 56 | 诊断结果；不能称为正确拒答 |
| 来源错误/跨项目来源输出 | 0 | 0 | 已保存输出、精确项目 scope 下的结果 |

每个阶段两版本都是 recall **48/56** 完整、目录 **8/8** 完整。失败完全保留：每个项目的 `multi_source` 查询都只命中必需的边界条件，当前策略缺失，`required_ranks = [null, 1]`。例如：

> What is the current edge_policy and which boundary constraints must pass?

`routing-archive:multi_source` 的返回列表是 `boundary-contract` 加四条 `maintenance-*`，没有 `current-policy`。原响应在 ZIP 内 `run/age-reference-1024/round0-candidate-attempt001/responses.jsonl.gz`；相邻 `observations.jsonl` 中该 case 的 `raw_gzip_offset` 与 `raw_gzip_bytes` 给出确切位置。报告 JSON 为所有失败配置保存相同定位信息，不需要重新检索。

此外，前四检查点每个英文 `current` 查询都将旧策略放在当前策略之前；中文查询在本轮排首位正确。进入自身历史增长的 100,000 页阶段后，两版本英文 current 均变为当前策略排首位，包括自身仍只有 16 页的归档项目。这是语料变化下两端同时出现的排名变化，不能记为候选算法改进。多来源失败仍然存在。

日期平移与交错写入对照中，每端各 72 个质量输出的 evidence projection 均不变。两端同一检查点的 504 个质量配置也没有证据 projection 或 score 差异。448 个 recall 原响应的稳定 JSON 有变化；直接字段差异核对表明新增 `temporal.evidence_assessment`（448 次）与 `warnings`（62 次），并非新的证据命中。

性能矩阵也包含失败输出：每端 **840 次** `training-core:multi_source` 性能调用证据不完整。其延迟仍原样计时并披露，不能因速度而算作正确答案。

## 性能结果

每性能查询、每版本、每检查点：冷 recall **n=30**，热结果缓存 **n=90**，无缓存目录完整链 **n=30**。共六轮，顺序 `AB, BA, BA, AB, AB, BA`；报告保存每轮配对的候选/基线 p50 比值及 CPU 时间。下表仅为本台机器的经验分位数，不是一般 SLA 或统计显著性结论。

按全部检查点与查询分组，冷 recall 候选 **41/49 组 p50 较慢**（最大约 6.18%），8 组略快；热结果缓存 **49/49 组 p50 较慢**（最大约 11.63%）；目录完整链 **14/14 组更快**。不应把不同缓存模式混合成一个总体加速数。

## 环境与审计边界

- 实际测量时间窗：2026-11-18 13:28:59–13:38:56 UTC。Ubuntu 24.04 hosted runner，Intel Xeon 6975P-C、4 个逻辑 CPU，Python 3.12.16，SQLite 3.45.1。
- 冷 recall 只在计时前清空 `recall_cache`；SQLite pager、连接辅助缓存和 OS 文件缓存没有全局清除。热结果缓存逐次确认 `cache_hit = true`。
- 计时不含恢复、打开库、评分和输出写盘；初始化单列。RSS 是进程生命周期峰值，不能当每个查询的独占内存分配，更不能据此宣称候选节省内存。
- 最大记录数据库快照 **384,495,616 bytes**。执行块记录的最大进程生命周期 RSS 为 **54.765625 MiB**。
- 独立 ZIP 复核核对 **166,409 项完整性条件、570 个 ZIP 文件、569 个文件清单 hash、13,608 个原响应、66,136 个原文引用**。逐条重新核对来源页 ID、项目、原文坐标、冻结 scorer、gzip 成员和稳定 hash；独立重算所有 p50/p95/min/max 和配对中位数比值。
- 本复核没有重新打开或恢复 CI 数据库。真实行数、快照 hash、源表 fingerprint 和逐 arm 恢复记录来自冻结的原执行记录，并彼此交叉核对。
- 本地源码逐文件对照指定 Git blob；CI native 导入路径/hash 证明与每个 worker 互相核对。原 hosted native 二进制未在本地恢复，不声称独立重建了该二进制。

## 后续判断

本轮支持“十万真实页、精确项目作用域下，保存来源均可回溯；目录完整链在已测配置更快”。它同时明确暴露多来源证据缺失、部分旧策略排首位、无证据查询仍返回上下文，以及 recall 延迟的额外开销和规模/布局敏感性。修复这些问题应创建新的源码与新执行记录；run 1 的协议、查询、gold、score、失败和原 ZIP 必须原样保留。
